# S10ykApp 技术方案

版本：v2.0 ｜ 日期：2026-11-14 ｜ 适用：山猫 S10 Pro（NOS: 10.21.33.106）

## 1. 目标与范围

在机器狗本体部署一套**远程遥控 + 语音播报**应用：手机/PC 连机器人 WiFi，打开网页即可控制运动（站立/趴下/急停/步行/转向）并触发语音播报。

v1.0 范围：
- ✅ 运动状态转换、步态切换、速度控制（含安全保护）
- ✅ 状态回显（运动状态、步态、速度、机身高度、里程）
- ✅ 语音播报（系统预置音效 + 自定义"保持3m距离"语音）
- ❌ 不做自由文本 TTS（按用户要求延后）
- ❌ 不做用户鉴权（LAN 信任模型，v2 再补）

## 3. 总体架构

```
┌────────────── 手机/PC 浏览器 ──────────────┐
│  index.html（单文件：十字方向盘/按钮/状态/语音）│
└───────────────┬────────────────────────────┘
                │ HTTP/JSON（100ms 方向盘节拍，500ms 状态轮询）
┌───────────────▼────────────────────────────┐
│  后端 app.py（stdlib http.server + rclpy）  │  8080
│  ├ S10Bridge(Node)：publish/subscribe       │
│  ├ nav_loop：20Hz 下发 /STEER + 三档速度档位 │
│  ├ DDS 通路：预置音效 /AUDIO/COMMAND         │
│  └ SAY 通路：ssh + aplay 推流（自定义语音）   │
└───────┬───────────────────────┬─────────────┘
        │ ROS2/DDS              │ ssh (10.21.33.103)
┌───────▼────────┐      ┌───────▼──────────────┐
│ /MOTION_STATE  │      │ aplay -D plughw:0,0  │
│ /GAIT          │      │ → ES8323 声卡 → 扬声器 │
│ /STEER         │      └──────────────────────┘
│ /MOTION_INFO   │      ┌──────────────────────┐
│ /AUDIO/COMMAND │─────▶│ 厂商 audio_node       │
└────────────────┘      │ （仅 9 条预置音效）    │
                        └──────────────────────┘
```

设计取舍：
- **纯标准库 HTTP**：板上无外网、装不了 fastapi/uvicorn，stdlib 方案零依赖、可长期稳定运行；v2 若开内网源可迁 FastAPI（接口保持 REST 不变）。
- **预置音效走 DDS 直发**（v1.1 起不再用 `audio_ctl`——实测其消息根本没送达节点，`ros2 topic pub` 才生效）。
- **自定义语音走 `ssh + aplay`**：厂商 audio_node 运行在独立安全容器内、只认自身私有资产副本（新增 ID 无效，详见缺陷 D-010），故绕过它直接驱动 103 声卡；零额外依赖、无需在 103 落盘（音频经 stdin 管道送入）。

## 5. 运动控制实现要点

- 消息类型（drdds 自定义，板上 `ros2 interface show` 可直接查）：
  - `MotionState{header{frame_id:uint64, stamp}, data.state:int32}`
  - `Gait{..., data.gait:uint32}`
  - `Steer{..., data.x/y/z/roll/pitch/yaw:float32}` ← **v2.9 起为实际运动控制通道**
  - `NavCmd{..., data.x_vel/y_vel/yaw_vel:float32}` ← 旧通道，保留但机器人不执行
  - `MotionInfo{data.vel_x/vel_y/vel_yaw/height + motion_state.state + gait_state.gait + remain_mile}`
- `header.frame_id` 递增计数、`header.stamp` 取节点时钟，保证时序合法。
- **控制通道是 `/STEER`，不是 `/NAV_CMD`（v2.9 关键结论）**：2026-11-16 用遥控器实测定性——`/NAV_CMD` 无论何种姿态/步态 `vel_x` 恒 0；遥控器走 `/STEER.data.x`，推杆时 `vel_x` 同向 1:1 跟随（详见 `遥控器控制通路实测_20261116.md`）。`NAV_CMD` 需 ASDU 切导航模式才生效，本应用不实现 ASDU。
- **20Hz 持续下发**：`nav_loop()` 以 `STEER_PERIOD_S=0.05` 发布；前端 100ms 节拍 + 保活，后端按 300ms 判活。
- **三档速度（REQ-033，2026-11-17 全量程实测重设）**：档位由前端按钮显式选择（`GEAR_IDX` 0/1/2=低/中/高，默认 **1=中速**），经 `POST /api/gear` 设置；`steer_gear()` 幅值只判方向/死区 0.15，速度大小按档位取值（不再按摇杆幅值 0.50/0.80 量化）。
  | 通道 | 低 | 中（默认） | 高 | 对应速度 |
  |---|---|---|---|---|
  | `data.x` 前后 | 0.16 | 0.47 | 0.81 | **0.3 / 0.8 / 1.3 m/s** |
  | `data.yaw` 转向 | 0.15 | 0.33 | 0.50 | ≈0.19 / 0.40 / 0.62 rad/s（左） |
- **标定关系**（全量程实测，见 `速度范围实测报告_20261117.md`）：`vel_x ≈ 0.064 + 1.510·x`（R²=0.993）；转向左 `vel_yaw ≈ 1.22·yaw`、右 `≈1.32·yaw`。饱和点 x≈1.0–1.1（约 1.3–1.5 m/s），超过只增超调不增稳态速度。
- **物理限制**：前后有 **0.15 m/s 最小步速地板**（无蠕行档）；左右平移 `data.y`/`data.z` 机器人不读，**无横移通道**（只能转 90° + 前进）。档位值按当前工况（开阔地、边充电）实测，电压/载重/地面变化会影响实际速度。
- **零值保持（关键安全项）**：松手/断流后 20Hz 连发零 **1.5s**，之后降 2Hz 保活——实测刹停有 1.5~2s 惯性，只发一帧零会继续漂；急停则先连发零 0.6s 再撤 ARM。
- **安全设计**：默认未 ARM，且未 ARM 时 `nav_loop` **完全静默**（不干扰遥控器同发 `/STEER`）；ARM 状态 500ms 同步；前端 `window` 级 pointerup/blur 兜底归零。
- **标题行开关（REQ-023 / REQ-034）**：运动控制 `#armBtn`（速度使能）与摄像头 `#camBtn`（视频开关，REQ-034 由文字按钮改来）统一用 `button.sw` 滑动开关——关态灰底（`#cbd2dc`）滑块居左、开态绿底（`--ok`）滑块 `translateX(18px)`，0.18s 过渡，按钮内仅 `<i>🔒/🔓</i>` 无文字；含义靠 `title` + `aria-label`。对应 `setArm(v)` / `setCamOn(v)` 同步 `classList.toggle("on")`、`title`、`firstElementChild.textContent`。纯前端，不涉及后端接口。
- 站立差异：ASDU（30003）路径下发站立会**自动进 RL**，而 ROS2 话题 `/MOTION_STATE` 只到半蹲——所以本应用用"1 → 等高 → 17"的序列补全（见 D-013）。
- 步态/模式常识（v2.5 实测补全）：切步态会**联动切运动模式**——`0x10xx` 常规模式（基础 `0x1001`、**高台 `0x1002`**、楼梯 `0x1003`），`0x30xx` 导航模式（平地 `0x3002`、楼梯 `0x3003`）。指南只列了 4 个值，高台 `0x1002` 是实测抓到的（官方遥控器按下后 `/MOTION_INFO` 上报 `0x1002`，机身由 0.387 m 降到 0.357 m）。`/STEER` 在导航步态 0x3002 与常规步态 0x1001 下均已实测有效（见 D-005 / D-029）。
- **站立必须两步（v1.3 关键）**：话题 `/MOTION_STATE` 下发 `state=1` 只完成"起立"，机器狗**不会自动进 RL**（指南 2.2.1），此时机身停在半蹲。实测高度：
  | 状态 | state | 机身高度 |
  |---|---|---|
  | 趴下 | 4 / 空闲 0 | 0.080 m |
  | 站立（半蹲） | 1 | 0.2266 m |
  | 站立 + RL（遥控器姿态） | 17 | **0.3865 m** |
  实现：`POST /api/motion/state {state:1}` → 后端线程 `stand_sequence()`：发 1 → 轮询 `/MOTION_INFO` 直到高度 ≥0.20 m 且连续 3 帧稳定（抖动 ≤2 mm，超时 8 s）→ 补发 17；到位后 gait 自动为 4097（基础 0x1001）。

## 6. 语音播报实现（v1.2 重构，v1.4 增加循环开关）

### 6.1 两条链路

| 场景 | 链路 | 说明 |
|---|---|---|
| 系统预置音效（9 条，id 1/2/3/4/5/6/7/100/101） | `/AUDIO/COMMAND` → 厂商 audio_node | DDS 直发，`Float64MultiArray` = `[op, id, interval_ms, repeat, priority, preempt]` |
| 自定义语音（任意内容 wav） | TCP → 103 常驻 `sayd`（:18081）→ `aplay -D plughw:0,0` | **v2.4 起**：按需开设备、播完/停止即释放，不在 103 落盘（旧实现为 `ssh + aplay` 管道，已废弃） |

### 6.1.1 循环播报（v1.4）

| 链路 | 循环实现 | 间隔 |
|---|---|---|
| 预置音效 | `/AUDIO/COMMAND` 的 `repeat=0`（无限循环），`preempt=1` 便于新播报抢占 | audio_node 每轮之间约 0.5 s 静默 |
| 自定义语音 | `say_wav(file, loop=True)`：后端按 `byte_rate` 实时节流，每 100 ms 推一片 3200 B 给 `sayd`；播完一轮再发一次 `START` 重开设备 | 默认无间隙；`SAY_LOOP_GAP≥1.4` 时轮次间真正释放设备（给厂商提示音留窗口） |

- 开关位于「语音播报」标题右侧（`div.cardh` 两端对齐），文案只有「循环开」/「循环关」两态；状态存浏览器 `localStorage["s10yk_loop"]`，默认关（单次）。
- **两路互斥**：`/api/audio/play` 与 `/api/audio/say` 入口先执行 `audio_stop(0)` + `say_stop()`，避免 DDS 循环与 aplay 同时占用声卡（曾出现 aplay `BrokenPipeError` 与叠音）。
- 停止：`/api/audio/stop` 同时 `say_stop()`（发 `F_STOP` + 断链，必要时补发"孤儿 STOP"）与 `audio_stop(0)`（DDS 全停）。
- 循环不再预生成 15 分钟流，由后端逐轮驱动，用户随时点停止即时生效（≤100 ms）。

### 6.2 为什么不能用「新增 audio_id」

实测结论（详见缺陷 D-010）：

1. 厂商 audio_node 运行在 103 侧的独立安全容器内，`ps`/`/proc` 均不可见；
2. 它日志里打印的 `config=/opt/robot/share/robot_drivers/audio_node_assets/audio.yaml` 是**它自己容器内的同名路径**，与 NOS（10.21.33.106）上我们改的那份不是同一个文件；
3. 决定性验证：把 NOS 上 `wav/default/连接成功.wav` 挪走后再播 id=4，日志显示正常播放完整 1.19 s → 节点读的是私有副本，改 NOS 侧文件永远无效；
4. 节点启动时一次性读完 9 条并缓存，新增第 10 条需要它重启，而我们无法从外部重启该容器。

因此 v1.2 放弃新增 ID，改为直驱 103 声卡；`audio.yaml` 已还原为原厂 9 条（备份保留在 `/S10ykRemove/backup/`）。

### 6.3 自定义语音制作流程

1. 开发机 `edge-tts`（zh-CN-XiaoxiaoNeural，-8% 语速）生成 mp3；
2. NOS 上 `ffmpeg -ar 16000 -ac 1 -c:a pcm_s16le` 转 wav（与系统音效同格式）；
3. 落 `/S10ykRemove/app/assets/你的名字.wav`；
4. 在 `assets/manifest.json` 加显示名：`{"voices":[{"file":"你的名字.wav","name":"中文显示名"}]}`；
5. 刷新网页即出现在语音面板（id 从 1000 起，`say:true`）。

### 6.4 依赖与注意

- 免密钥 SSH：`/S10ykRemove/app/keys/id_s10yk`（ed25519），公钥已加入 103 的 `~/.ssh/authorized_keys`；OTA/重置后需重放公钥（见操作记录 OPS-07）。
- 播放互斥：后端同一时刻只保留一个 `aplay` 进程，新播报自动终止上一条。
- 音量：103 声卡 ES8323 的 `PCM` 混音（0–192 → 0–100%，出厂 88%）。**v2.0 起默认锁 100%**：
  - 启动 `set_volume(100)`；`volume_keeper()` 每 10 s 巡检，漂移即拉回（覆盖重启回落/外部改动）；
  - 两条播报通路（DDS 预置、ssh+aplay 自定义）共用同一张声卡，故一处设定对两者同时生效；
  - `/api/status` 上报 `volume` / `volume_target`，前端状态卡「音频」格以 `100%` 为主值、播放状态为副行。

### 6.6 播报框选态与状态回收（v1.8）

| 项 | 实现 |

|---|---|
| 数据源 | DDS 话题 `/BATTERY_DATA`（`drdds/msg/BatteryData`，`.data[0]` 为 `BatteryDataValue`） |
| 字段换算 | `voltage/100→V`（10mV）、`current/100→A`（10mA）、`battery_level→%`、`max(battery_temperature)→℃`、`cycles` 直读 |
| 后端 | `on_battery()` 订阅缓存 `BATTERY_INFO{level,voltage,current,temp,cycles,ts}`；`/api/status` 返回 `battery` 对象 |
| 前端 | 状态卡改 5 列同行（`repeat(5,1fr)`，主值字号 15→14px 防溢出）；主值 `xx%`，<20% 橙 / <10% 红；副行 `71.98V 26.9℃` |
| 充电判定（v2.2） | `current > +0.3A` → `charging=true`（实测充电 +1.6A、放电 -0.7~-1.4A）；UI 主值转绿 + 副行前缀 ⚡ |
| 备注 | 开发指南未记载 `/BATTERY_DATA`（指南只在 ASDU 设备状态上报 JSON 的 `BatteryList` 提供电量）；`mos_state` 在充电/放电时均可能为 2/3，无法作为充电判据 |

### 6.8 音频通路改造（v2.4：从"抢占声卡"到"按需占用 + 播完即还"）

**前置判定：自定义语音无法 100% 话题化**（详见审计文档第 8.2 节）
- `/AUDIO/COMMAND` 报文无"文件/PCM"通道（`op` 仅 0=PLAY 按 id、1=STOP）；
- `audio.yaml` 启动时一次性载入、无热加载，新增 id 需重启节点，而节点在第三个隔离容器内不可重启；
- 该容器使用私有资产副本（挪走 106 同名 wav 后播 id=4 仍出声）。
→ 属接口能力限制，不是实现选择。

**三条决定设计方向的实测事实**

| # | 事实 | 设计含义 |
|---|---|---|
| 1 | 话题播放确实占用 103 `card0`（`appl_ptr` 持续推进） | 与厂商共用同一播放子设备，必须协调 |
| 2 | 我方占设备时厂商播报 **20 ms 内放弃**（不排队重试） | "暂停推流但不关设备"无用，**必须真正 close** |
| 3 | `repeat=0 + preempt=WAIT` 会静默卡死厂商调度器 | 一律"先 STOP 再以 FORCE 下发"，并做状态回执判定 |

**sayd 协议（103，`/opt/s10yk/sayd.py`，systemd `s10yk-say`，`Restart=always`）**

| 帧 | 格式 | 语义 |
|---|---|---|
| `F_START=1` | `>BI` + JSON `{rate,channels}` | 打开 `plughw:0,0`，回 `OK\n`；已有会话回 `BUSY\n` |
| `F_PCM=2` | `>BI` + PCM 分片 | 写入 aplay stdin（3200 B/片 = 100 ms） |
| `F_STOP=3` | `>BI` len=0 | 结束 aplay、close 设备、回 `OK\n` |
| `F_PING=4` | 心跳 | 保活（空闲 1.2 s 自动释放设备） |

**后端要点**
- 连接失败自动 `systemctl restart s10yk-say` 后重连一次（免人工）。
- 推流按 `byte_rate` 实时节流、`SO_SNDBUF=8192` → 停止 ≤100 ms 生效（旧实现一次灌满内核缓冲，停止要等播完）。
- `say_stop()` 双路径：连接在 → `F_STOP`+断链；连接已被推流线程断开 → 另开连接补发一帧"孤儿 STOP"。
- 预置音效 `play_preset()`：STOP 清场 → FORCE 下发 → 500 ms 内无 `/AUDIO/STATUS` 翻转视为卡死 → STOP 重试一次。
- 音量巡检 20 s → 60 s。

**为什么没选另一条路（`/AUDIO/STATUS` 协作避让）**：事实 2 说明厂商不会等我们让路，它只会立刻放弃；因此协作式避让在"持续播放"场景没有意义，只能靠减少占用时长 + 播完立即归还。

**v2.5 追加：真混音可行性已定性（详见审计文档第十节）**

| 结论 | 依据 |
|---|---|
| 硬件层做不到多流 | card0 `Subdevices: 1/1`，第二进程裸开 `plughw:0,0` → `Device or resource busy` |
| **dmix 本身可用** | 同一 card0 上配 `pcm.dmixed`（slave `hw:0,0`），两个客户端并发播放均成功，底层仅一个 `owner_pid` |
| 但厂商不走 dmix | dmix 持卡时下发 `/AUDIO/COMMAND`，`/AUDIO/STATUS` 恒 `state:0`（一声未出）；反向则 dmix `unable to open slave` |
| 配置改不动 | `audio.yaml` 的 `play:` 只有 `enable`/`volume`，**无 `device` 字段**；资产在隔离容器私有 rootfs |
| 虚拟声卡路不通 | `modinfo snd-aloop` → 模块未编译 |
| 板载无第二路 | card1（USB UAC）仅 capture；`Speaker`/`Headphone` 是同一 PCM 的两个模拟开关 |

→ 因此**不存在"纯软件且无需厂商配合"的混音方案**。可选：① 106 插 USB 小喇叭做物理第二路（推荐，零冲突、可回滚）；② 厂商在 `play:` 增 `device` 指向 dmix（一行，真混音）；③ 云端 `talk.recv`；④ 现状时间片让路（兜底）。

## 11. 访问控制（v2.7）

公网入口一开，控制台就从"同网段玩具"变成"任何人可控的机器人"。v2.7 加了口令鉴权。

```
浏览器 ──POST /api/login {token}──▶ app.py 校验 S10YK_TOKEN
                                      │ 成功：Set-Cookie: s10yk_token=…; HttpOnly; SameSite=Strict; 7d
                                      ▼
        后续所有 /api/*（含 <img src="/api/cam/stream">）自动携带 Cookie → 200
        无凭据 / 口令错 → 401 {"error":"unauthorized","auth":true}
```

**为什么是 Cookie 而不是纯 Bearer 头**：摄像头是 `<img src="/api/cam/stream">` 拉 MJPEG，`<img>` 标签**无法附加自定义请求头**；只有 Cookie 会被浏览器对同源请求自动带上。后端两者都接受（脚本/curl 用 Header 更方便）。

**鉴权边界**
| 路径 | 是否需要口令 |
|---|---|
| `/`、`/index.html`、`/favicon.ico` | 否（页面本身无敏感数据，登录层在前端） |
| `/api/auth`、`/api/login`、`/api/bw` | 否（必须放行：登录与带宽测速；`/api/bw` 仅返回固定填充块，无敏感数据，REQ-029） |
| `/api/status`、`/api/nav`、`/api/estop`、`/api/audio/*`、`/api/cam/*` … | **是** |

**口令存放**：`S10YK_TOKEN` 环境变量，用 systemd drop-in 注入（`*.service.d/token.conf`），不改原单元，便于轮换/摘除。留空则关闭鉴权（本机调试用）。

**轮换口令**：改 drop-in → `daemon-reload && restart` → 所有已登录会话下次请求即 401。

**残余风险**：明文 HTTP，Cookie 可被中间人嗅探（D-026）。要彻底需 HTTPS——此时才真正需要 nginx（8082 + 证书 + `proxy_buffering off` 保 MJPEG）。

## 12. 单向喊话 / 实时对讲（REQ-037 实施，REQ-039 升级）

- **定位**：手机麦克风 → 本体扬声器单向喊话；不含狗端收音（`/AUDIO/RECORD_CMD` 崩溃、`arecord` 硬件 busy，见审计文档）。官方 110 dBA 喊话属外挂"二代多合一"载荷，非本体能力（见调研 §11）。仅 Chrome + 自签 HTTPS。
- **两种模式**：`clip`（录完即播，松手整段 WAV 上传）与 `stream`（**实时对讲，当前 UI 使用**）。二者共用 `SHOUT` 会话态与 sayd 连接，`mode` 字段区分，UI 固定 `stream`。
- **复用基础**：喊话 = 给 103 板 sayd（TCP 18081）灌 PCM，与 `say_wav()` 同构，**sayd 协议与代码不改**。sayd 帧：`START{rate,channels}` / `PCM(S16_LE 片)` / `STOP`；全局单例 PLAYER，播完/空闲 1.2s 释放 plughw:0,0。
- **HTTPS 双监听**：单实例双端口（明文 18090 + TLS 18443）共用 Handler 与全局状态；证书 `/opt/s10yk/certs/`（自签 825 天，SAN 含 `IP:<SERVER_IP>`），systemd drop-in `tls.conf` 注入 `S10YK_TLS_CERT/KEY/PORT`。Chrome 首次访问点「高级→继续」信任后 `getUserMedia` 可用；换访问地址须把地址加进 SAN 重签。
- **接口**（`app.py`）
  | 方法 | 路径 | Body | 说明 |
  |---|---|---|---|
  | POST | `/api/shout/start` | `{rate,channels}` | 建会话、启看门狗（实时对讲主用） |
  | POST | `/api/shout/pcm` | 每片 ≤3200B PCM | 按序 F_PCM 推送，收到即写 aplay |
  | POST | `/api/shout/stop` | `{}` | 停会话（幂等） |
  | POST | `/api/shout/clip` | WAV 二进制 | 录完即播（保留，UI 已不用） |
  | GET | `/api/shout/state` | — | `{active,mode,seconds,bytes}` |
  | GET | `/shout-processor.js` | — | AudioWorklet 脚本（AUTH_OPEN 放行） |
  | — | `/api/status.shout` | — | 状态随主状态下发 |
- **低延迟改造（REQ-039）**：① HTTP/1.1 `keep-alive`（每秒 10 个 PCM 小包，HTTP/1.0 每包都要重做 TCP+TLS 握手）；② `Handler.timeout=65` 回收空闲连接、`disable_nagle_algorithm=True`；③ sayd socket 设 `TCP_NODELAY` + `SO_SNDBUF=8192`；④ `SHOUT_TX` 锁串行化写帧（并发写会把帧头帧体交错）。
- **会话与看门狗**：`SHOUT` 全局态与 `SAY` 并列；`_shout_watchdog` 5s 无新片 / 120s 超时自动 `_shout_clear()`（发 STOP、断链、pkill 僵尸 aplay）。
- **UI 结构（REQ-038）**：语音卡片标题为「语音」，标题行三同级页签 `语音播报|一键喊话|双向对讲`（`data-tab=say|shout|talk`，记忆到 `s10yk_audio_mode`，默认 say）；三面板 `#paneSay/#paneShout/#paneTalk` 用 `hidden` 互斥。**语音播报**只列自定义音频（系统音取消），停止播报/循环关下移到该面板首行两列；**一键喊话**仅保留「按住说话」按钮（实时对讲）；**双向对讲**为 `.soon` 占位「敬请期待」。离开 say 页签 `astop()`，离开 shout 页签在录音则 `shoutUp()` 否则 `POST /api/shout/stop`。
- **前端实时发送**：`shoutInitAudio()`（`getUserMedia` echoCancellation + AudioWorklet 每 100ms 产 3200B，ScriptProcessor 兜底）→ `onPcm` 入队 → `shoutPump()` **串行**发送（单请求在飞保序；最多合批 4 片/400ms）→ 队列上限 15 片（1.5s），超出丢最旧并计数 → 松手 `shoutDrain(1500)` 排空后再 `/stop`；409 自动重建会话一次；`SHOUT_GEN` 代次保护防止旧收尾误停新会话；`setPointerCapture` 使手指滑出按钮不断话。
- **延迟构成**：客户端采集 100ms 切片 + 网络 RTT + sayd 管道（近空） + **aplay 缓冲**。缓冲已于 OPS-64 从默认 ≈500ms 收到 **250ms**（`-B 250000`，周期 `-F 50000`）：sayd 侧参数 `SAYD_BUFFER_US/SAYD_PERIOD_US` 可调，实测 ALSA 协商 `buffer_size 4000 frames / period 800 frames @16k`（正好 250ms/50ms），预期实听 0.35~0.6s。代价是 Wi-Fi 抖动 >250ms 时更易 underrun（出咔哒/短暂静音）——现场若出现断续，优先把 `SAYD_BUFFER_US` 回调到 400000，而不是减小分片。
- **互斥**：喊话与 DDS 预置音 / sayd 自定义播报三路共享声卡——`/api/audio/{play,say,stop}` 与 `say_wav()` 内均调 `shout_stop()`，反之喊话前 `say_stop()`+`audio_stop(0)`+pkill。
- **边界**：PCM 无会话 409（前端自动重建一次）、单片 >128KB 400、非法/超大 clip 400、非 16bit 拒绝；仅 Chrome+HTTPS，其它浏览器提示不支持。
- **验收**：见 OPS-61（clip/会话/看门狗/互斥）与 OPS-63（实时推流、keep-alive、MJPEG 回归）；真人口播听感待现场确认。

### 12.1 双向对讲与 MIC 抢占计数（REQ-041 / D-034 衍生）

- **下行通路**：后端 SSH 到业务板拉 `stdbuf -o0 arecord -D plughw:1,0 -f S16_LE -r 16000 -c 1 -t raw -B 200000 -F 40000 -`（card1 USB 麦阵列，6ch 设备受 1ch；`stdbuf -o0` 关 stdio 缓冲，否则块缓冲白加 128ms）；40ms/1280B 一帧 → `TALK_Q`（≤40 帧丢最旧）→ `GET /api/talk/pcm` chunked 推流 → 前端 Web Audio 排队播放（2 字节对齐、起播缓冲 120ms、掉队跳当下不追积压、下行增益 0.9）。上行复用 12 的 shout 通路——两侧同时跑即双向。
- **不在 sayd 里做采集**：sayd 是「按需开、播完即关」的播放器，加采集会让它长期占麦，与厂商节点/会话生命周期纠缠；采集管道随对讲会话生灭。
- **MIC 抢占计数**（D-034：厂商 audio_node 未停、随时可能夺麦）：开麦即 busy / 中途进程退出 / 5s 卡死 → `preempt+1`（会话内）与 `preempt_total+1`（累计）；300ms 后自动重开，单会话 ≤3 次，用尽则会话结束（`why:"mic-lost"`）。前端常显「MIC 被抢占 N 次（本次 M）· 原因」，≥1 次转红。忙等语义：`talk/start` 等首帧 ≤3s，失败即返 `ok:false+err`。
- **会话守恒**：无消费者 20s 自动收麦（`TALK_IDLE_S`）、单次 ≤600s、看门狗 + `stream_gen` 让挂起的 chunked 推流立即退出；`/api/status.talk` 每 500ms 下发全部计数。
- **互斥（D-035 教训）**：`/api/audio/{play,say,stop}` 与 `say_wav()` 同时停 shout 与 talk；talk 自身 start 前先 `say_stop()`+`audio_stop(0)`。所有「锁内读标志、锁外清理」——`threading.Lock` 不可重入，锁内调用会再次取锁的函数必死锁。
- **已知限制**：下行 1ch（麦阵列第一路，未 6ch 下混）；回声靠手机 AEC + 增益 0.9，外放大音量可能回授（建议戴耳机）；预期下行延迟 ≈ 40ms 采集 + SSH/HTTP + 120ms 起播 ≈ 0.3~0.5s（未实测听感）。
- **验收**：见 OPS-67（首帧 0.6s、32KB/s 实时率、被夺自愈、busy 计数 1+3 重试、无残留、幂等无死锁）。
