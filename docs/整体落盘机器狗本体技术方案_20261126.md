## 二、目标架构

```
┌─────── 手机/PC 浏览器（现场 WiFi）───────┐
│   https://10.21.33.103:18443 或
│   https://<ROBOT_IP>:18443          │
└──────────────┬──────────────────────────┘
               │ HTTP/HTTPS + Cookie 鉴权 + PCM 流（全部本机回环/内网）
┌──────────────▼────────────────────────────────────────────┐
│ 业务板 10.21.33.103（<ROBOT_IP>）— 全部应用落盘于此      │
│  s10yk-backend   :18090 明文 / :18443 TLS（新 systemd 单元）│
│  s10yk-persond   :无端口，文件型（新 systemd 单元）          │
│  mic_front.py    :由后端本机 subprocess 拉起（免 SSH）       │
│  sayd.py         :18081（现有 s10yk-say 不动，后端直连）     │
│  /opt/s10yk/{backend,frontend,models,certs,assets,data}   │
│  ROS2 Jazzy（已在位）+ drdds aarch64（自 106 离线迁移）      │
└───────┬──────────────── DDS domain 0（已验证直通）─────────┘
        │ eth0 10.21.33.0/24（实测 RTT 0.34ms，多播发现正常）
┌───────▼───────────────────────────────────────────────────┐
│ NOS 板 10.21.33.106 — 零改动：/MOTION_* /GAIT /STEER /AUDIO │
└───────────────────────────────────────────────────────────┘
（可选）205 装 frpc → frps(<FRP_IP>):7306→18443，公网访问不经过 204
```

核心结论：**业务板一板承载全部应用，NOS 板零改动**。两块板的分工 = 103 跑应用 + 106 提供 ROS2/DDS 运行时（现状延续）。

## 三、DDS 通路与 drdds 迁移（方案成立的关键，已实测预验证）

1. 205 宿主机 source `/opt/ros/jazzy` 后 rclpy 可发现全部业务话题（实测 ✅，默认 domain 0 与 drdds.env 一致）。
2. 缺口仅剩 **drdds 消息包**（205 的 jazzy 没装）：从 106 `dpkg -L` 定位文件（lib/libdrdds__rosidl_*.so + lib/python3.12/site-packages/drdds + drddslib 运行时），tar 打包 → 解到 205 `/opt/ros/jazzy`（**同 aarch64、同 Jazzy 版本，直接落位**，dpkg 层面不注册，避免干扰厂商包管理）。
3. 实施第一步先做 **类型兼容冒烟测试**：205 上以 Steer 类型发布 /STEER 一帧 + 订阅 /MOTION_INFO 收包成功才继续；不通过则启用备选方案 B（rclpy GenericPublisher，免 drdds 包，需小规模重构）。

## 四、SSH 通路本机化（消除对内网 SSH 依赖）

现状：204 后端经 SSH 到 205 做 4 件事——amixer 音量、sayd systemd 重启拉起、mic_front 拉起、talk arecord 管道。落盘后两个选项：

- **选项 A（零代码改动）**：`S10YK_SAY_HOST=user@127.0.0.1` + 本机生成密钥写入 authorized_keys。快速、无代码风险。
- **选项 B（推荐，小改动）**：`_ssh103()` 增加本机直执行分支（SAY_HOST 为空或 "local" 时 subprocess 直跑），mic/arecord 管道同步本机化。去掉每次 SSH 开销（音量调节延迟改善），实施时附回归验证。

## 六、与 204 云控系统的共存与切换（互斥资源，不是端口问题）

DDS 话题（/STEER /AUDIO/COMMAND）、声卡、MIC 都是**独占资源**——两套 backend 同时运行会双写 /STEER（运动指令打架）+ 争抢声卡/MIC。因此：

1. **切换日**：205 新服务验收通过后，204 执行 `systemctl stop s10yk-backend s10yk-persond && systemctl disable ...`（数据与文档保留，可随时回滚）。
2. **共存期**（切换前的并行验证）：204 系统保持运行，但 205 新 backend 只做**只读验证**（订阅遥测、拉视频、本地页面打开），不发 /STEER、不播语音；对讲/喊话类写操作只在 204 侧测试，避免互相打断。
3. zenoh-bridge-dds（205 上连 204:7447 的进程）：切换完成、204 停服后一并 stop+disable（不再需要）；若保留也不与新架构冲突，但白耗 CPU（现占 20%）。
4. 204 的 frp 映射（7301 SSH/7302 RTSP）：保留可作应急带外通道；205 自建 frpc（可选）用 **remotePort 7306** 起步，避开 204 已占的 7300-7305。

## 八、ARM 性能预案（人员检测）

x86(204) 8 线程 1280 单帧 ≈190ms；205 为 ARM 核且底噪 load 3.5+，预估单帧显著变慢。预案阶梯：

1. 首选：1280 输入 + **4 推理线程 + 2fps 节流**（PERSON_THREADS/PERSON_FPS 环境变量，代码已支持则直接用，否则小改）；
2. 实测丢帧率 >30% 或 CPU 打满 → 回退 640 模型（≈30m→13m 距离损失，需告知用户确认）；
3. 底线：persond 仅作抓拍预警非实时需求，可接受 1fps。

## 九、安全

- **S10YK_TOKEN 必配**（顺带修正当前 204 鉴权 OFF 的隐患；前端已有登录页）。
- 证书本地 openssl 生成，SAN 含两个 IP；公网访问（可选 frp 7306）时浏览器信任自签证书照常手动放行。
- 落盘后控制台暴露面 = 现场 WiFi + 可选单端口 frp，较现状（ufw 全公网开放 18090/18443 + 无鉴权）**攻击面显著收窄**。

## 十一、回滚

任一步失败：205 新服务 `disable --now`，204 `systemctl start s10yk-backend s10yk-persond` 即恢复原架构（原 204 部署全程不动，仅停/启）。
