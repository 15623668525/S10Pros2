## OPS-10 站立姿态问题定位与修复（v1.3，2026-11-14 10:15–10:35）

背景：现场反馈网页「站立」后机器狗为半蹲，与厂家遥控器的站立姿态不一致。

**1. 查权威定义**（本地《S10 软件开发指南0915.pdf》2.2.1）
```bash
pdftotext/ PyMuPDF 提取  →  站立=1 / 关节阻尼=2 / 趴下=4 / RL控制=17
【注意】通过话题下发站立指令后，机器狗不会自动切换至 RL 控制状态
```

**2. 实测高度曲线**（板上探针订阅 /MOTION_INFO，每 1s 打印）
```bash
# 发 state=1
t=0s state=0 height=0.0797 gait=0      # 趴下
t=4s state=1 height=0.1832 gait=0      # 正在起立
t=5s state=1 height=0.2266 gait=0      # 停在半蹲（后续 25s 不变）
# 再发 state=17
t=4s state=17 height=0.3834 gait=0
t=5s state=17 height=0.3860 gait=0     # 全站姿，与遥控器一致
```
结论：**半蹲=只发了 1 未发 17**。遥控器走 ASDU 路径，站立完成后自动进 RL，所以没有这一步。

**3. 代码修复**
- `app.py` 新增 `stand_sequence()`：发 1 → 等高度≥0.20 且连续 3 帧稳定（≤2 mm）→ 补发 17，超时 8 s，遇 state=4 中止。
- `POST /api/motion/state {state:1}` 改为起线程执行该序列，返回 `{"ok":true,"seq":"stand(1)->rl(17)"}`。
- 前端「站立」按钮改调 `stand()`，状态区显示"起立中…"，版本 v1.3。

**4. 部署与验证**
```bash

## OPS-19A 插/拔充电指示延迟差实测（2026-11-14 13:51，v2.3 期间）

## OPS-26 访问鉴权上线（v2.7，2026-11-15 09:40–09:55）

**背景**：公网 20081 已开但无鉴权（D-003 升级为上线阻塞项），任何人知道地址即可控狗。

**1. 方案选型：为什么用 Cookie 而不是纯 Header**
| 方案 | 问题 |
|---|---|
| `Authorization: Bearer` 头 | 摄像头是 `<img src="/api/cam/stream">`，**`<img>` 标签无法附加自定义请求头**，流会被 401 挡死 |
| URL `?token=` | 会留在浏览器历史、Referer、frp/nginx 访问日志里，泄漏面大 |
| **Cookie（选定）** | 浏览器对同源 `<img>`、`fetch` 都自动带上；配 `HttpOnly` 防 XSS 读取 |

后端**两者都接受**（Header 或 Cookie），前端走 Cookie，脚本/curl 调试走 Header。

**2. 后端改动（app.py，v2.6→v2.7）**

AUTH_TTL = 604800                                        # 7 天
AUTH_OPEN = ("/", "/index.html", "/favicon.ico", "/api/auth", "/api/login")

# do_POST : /api/login 校验后 Set-Cookie HttpOnly;SameSite=Strict;Max-Age=7d

```

### OPS-32 补充：协议确认（Nooploop uBeacon Tag UART V1.8，2026-11-16 16:45）

设备为 **Nooploop（深圳无穹创新）uBeacon Tag** 标准精度 UWB 定位标签。协议文档 `uBeacon_Tag_UART_Protocol_V1.8_en.pdf`（工作区根目录）。

**帧格式（Table 3）**：`0xAA` + `PayloadSize(uint16)` + Payload + `Checksum(uint8, 前面所有字节相加取低 8 位)`
Payload = `UID(6B)` + `FrameID(1B)` + `MsgID(1B)` + `MsgLen(1B)` + `MsgPayload`；帧总长 = PayloadSize + 4。

**实测帧（msg_id=0x44 MSG_LOCATION_RESULT）字段偏移**
| 偏移 | 字段 | 类型 | 说明 |
|---|---|---|---|
| 0 | Frame Header | u8 | 0xAA |
| 1–2 | Payload Size | u16 LE | 57/61/65/69/73 |
| 3–8 | UID | 6×u8 | 本机 `02 04 07 30 07 25` |
| 9 | Frame ID | u8 | 5 = Serial_Frame_Tag_Up |
| 10 | Msg ID | u8 | 0x44 = MSG_LOCATION_RESULT |
| 11 | Msg Payload Len | u8 | = 36 + 4×AnchorCount |
| 12–19 | Location_time | u64 LE | **单位 us**（实测：1056668357 ≈ 17.6 min，与插入时长吻合） |
| 20–31 | Pos[3] | 3×f32 | x/y/z，单位 **m** |
| 32–37 | Vel_cm[3] | 3×i16 | cm/s，除以 100 得 m/s |
| 38–40 | Pos_noise_cm[3] | 3×u8 | cm |
| 41–43 | Vel_noise_cm[3] | 3×u8 | cm/s |
| 44 | Map_id | u8 | 当前地图 ID |
| 45 | Error(低4b)/Area(高4b) | u8 | — |
| 46 | Reserved | u8 | — |
| 47 | Anchor_count | u8 | 2~6 |
| 48+ | Anchors[n] | n×4B | Addr(u16) + Rx_rssi(u8, dBm = −v/2) + Rx_rate(u8, /255) |
| 末字节 | Checksum | u8 | 前面全部字节求和 & 0xFF |

**实测结果（8 秒 / 184 帧）**
- **校验和 184/184 全部通过**（0 失败）→ 帧同步与解析完全正确
- 帧率 23.0 fps；帧长 57~73 完全符合 `49 + 4×AnchorCount`（anchor 2~6 个）
- 位置：x 81.957~82.284 m，y 33.240~34.151 m，**z 恒定 3.602 m**（跨度仅 2 mm）
- 速度：−0.09 / −0.06 / 0 m/s（标签静止）
- 定位噪声：位置 6~16 cm，速度 18~27 cm/s
- Map_id=9，Error_code=0（定位有效），Area_id=1/2
- 可见基站 RSSI −45.5 ~ −86.5 dBm，rx_rate 0.73~0.89

**两个待确认点**
1. **z = 3.602 m 恒定不动**：噪声跨度只有 2 mm，说明 Z 轴被固定住了，多半是 `MSG_LOCATION_PARAM.Expect_z` 被设成了 3.6。若按地面作业的机器狗用，应改成标签实际安装高度（约 0.4~0.5 m），否则高度维完全不可信。
2. **丢帧约 20%**：Location_time 间隔中位 32.9 ms（设备约 30 Hz 输出），实测只收到 23 fps。带宽不是瓶颈（1495 B/s @ 115200 可用 11520 B/s），是读取端消费不过来，长期跑需改用阻塞大缓冲读取。

**注意**：`/dev/ttyCH343USB0` 是厂商自定义驱动命名，pyserial 直接 `serial.Serial('/dev/ttyCH343USB0', 115200)` 可用。

## OPS-36 运动控制「无效果」定位：NAV_CMD 通道对机器人无效（2026-11-16 20:21–21:10）

## OPS-37 遥控器实测：坐实有效通路是 `/STEER`（2026-11-16 20:56–20:58）

### 背景

OPS-36 得出"`/NAV_CMD` 对机器人无效"，但留了个关键问号：**用户说遥控器平时能让狗走**。若遥控器能走，就说明问题在接口选择而非链路。用户本次主动用遥控器（网络连 10.21.33.103）推前后杆，要求监听 2 分钟取实证。

### 方法

106 上起两路监听（`setsid nohup` 常驻 120 s）：

1. `rc_listen.py` —— Python 订阅 `MOTION_INFO`（2404 帧，20 Hz）+ `NAV_CMD`（303 帧，他人注入）
2. `ros2 topic echo` × 5 —— `/STEER`、`/HANDLE_STEER`、`/REAL_STEER`、`/ROBOT_CMD_INSTRUCTION`、`/GAIT`，`stdbuf -oL` 落盘

事后用 `align_steer.py` 把 `STEER.data.x` 与 `vel_x` 逐秒对齐。

### 结果（决定性）

| 相对时间 | STEER.x | vel_x (m/s) | gait/state | 现场 |
|---|---|---|---|---|
| 0–40 s | 无 | 0.0000 | 0/0 | 趴着 |
| 40 s | +0.750 | 0.0000 | 0/0 | 推杆 |
| 42 s | — | 0.0000 | 0/**1** | 站起 |
| 44 s | — | 0.0000 | 0/**17** | 进运动态 |
| 46 s | — | +0.0269 | **4097**/17 | 步态自动切 4097 |
| 48 s | — | **+0.3269** | 4097/17 | 前进 |
| 52–100 s | +0.34 / −0.57 交替 | −0.4819 ~ +0.4215 | 4097/17 | 前后反复 |
| 102 s | −0.44 → 0 | 0 | 0/**4** | 趴下 |
| 104–120 s | 无 | 0.0000 | 0/0 | 静止 |

**`STEER.x` 与 `vel_x` 正负同向、1:1 跟随，滞后 <1 s。遥控器确实能控狗，通路是 `/STEER`。**

### 附带确认

- `/STEER` 是**事件型**：只在推杆时发，静止不发（不是常发 10 Hz），所以"没数据"≠"通道断"。
- `/STEER` 与 `/HANDLE_STEER` 帧数、min/max 完全一致 → 同一份摇杆量的镜像。
- `/REAL_STEER`、`/ROBOT_CMD_INSTRUCTION` 全程 **0 帧**。
- 发布者全为 `_CREATED_BY_BARE_DDS_APP_`（厂商裸 DDS SDK）；`ros2 node list` 只见 `s10yk_bridge` / `traversability_estimation_node` / `ubeacon_driver`，遥控接收节点不可见。
- 站起后 gait 自动 4097 —— OPS-36 的 `stand_sequence()` 修复再次生效。

### 结论与下一步

- **控制台应改发 `/STEER`**（后端已有 `drdds/msg/Steer`，零新依赖），而不是继续折腾 NAV_CMD / ASDU。
- **前置必做：量纲标定**。观测 x=0.75 → vel_x≈0.33，疑似 −1~+1 归一化，**误按 m/s 下发会超速**。标定方法：分档发 x=0.02/0.05/0.10，读 `vel_x` 拟合 k；起步限速建议 `|x| ≤ 0.10`，且每帧后补 `x=0`。
- 未验证：`data.y`（左右）、`data.yaw`（转向）语义；遥控与后端同时发谁覆盖谁。

| 层 | 方法 | 结果 |
