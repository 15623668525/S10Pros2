# 视觉跟踪（目标锁定跟随）技术方案调研

- **需求编号**：REQ-050（点击锁定 + 视觉伺服）／REQ-051（手势锁定与解除）
- **日期**：2026-11-27
- **状态**：调研稿，待评审后进入 P1
- **一句话**：用前视摄像头框住一个人，狗自动转向/走位让人始终处于画面正中心，点击或手势结束

## 1. 需求拆解

| 编号 | 功能 | 说明 | 优先级 |
|---|---|---|---|
| R1 | 目标锁定 | ① 前端点击/框选画面中的人 ② 特定手势触发（举手） | P0 |
| R2 | 目标跟踪 | 逐帧维持对锁定人的身份绑定（遮挡、交叉、短暂丢失可恢复） | P0 |
| R3 | 居中伺服 | 以**前视画面正中心**为目标点，闭环修正转向（yaw）；后期标定垂直位置 | P0 |
| R4 | 距离保持 | 依据目标框高估算距离，维持 1.5–2 m（先做可选） | P1 |
| R5 | 结束跟踪 | 按钮结束（P0，必做）＋ 手势结束（双手交叉，P1） | P0/P1 |
| R6 | 安全兜底 | 丢目标停、断线归零、急停最高优先级、限速 | P0 |

**验收指标（P1 结束）**：锁定后 5 s 内居中（|横向偏差| < 画面宽 10%）；目标以 0.5 m/s 横移时可跟上；丢目标 1.5 s 内停车；急停响应 < 200 ms。

## 2. 现状盘点（全部为实测/代码事实）

| 能力 | 现状 | 对本需求的含义 |
|---|---|---|
| 4 路摄像头 | video0 后视 / video2 左视 / **video4 前视** / video6 右视；原生约 1024×576；RTSP 8554 | 前视为主伺服相机，左/右视可做失去目标后的重捕获（P2） |
| 取流 | 后端 ffmpeg → 960 宽 / 15 fps MJPEG（`nobuffer/low_delay/max_delay=0` 低延迟参数），进程内帧总线多客户端共享 | 跟踪器可直接从该总线取帧，无需新开 RTSP |
| 检测 | YOLOv8n ONNX：1280 输入 ≈190 ms/帧（8 线程 A55）、640 ≈42 ms/帧；现网 4 路 2–3 fps、**命中才落盘**（latest.json + 8 s 冷却） | 现成检测**不能**直接用（无实时框流、频率太低），需新增跟踪专用快速通路 |
| 运动通道 | `/STEER` 单帧带 `x`+`yaw`，20 Hz 续发；ARM 后生效；未更新 >0.3 s 自动归零（现有 `nav_loop` 天然 fail-safe） | 控制器只需以 ≥3.3 Hz 写 `NAV_CMD` 即可，无需改运动链路 |
| 档位量化 | 前端档位把摇杆映射为 x=0.16/0.47/0.81（0.3/0.8/1.3 m/s）、yaw=0.15/0.33/0.50（0.19/0.40/0.62 rad/s） | 跟踪需**连续量**：新增 TRACK 源直接写 ±0.5 内浮点，绕过档位量化 |
| 实测动力学 | 最小步速地板 ~0.15 m/s；刹停惯性 1.5–2 s；转向左右不对称（±0.12 输入 → +0.098 / −0.154 rad/s）；组合 x+yaw 时角速度衰减 20–26% 且抖动；转向归零残余阻尼 ~0.8 s | 控制律必须带死区、左右分增益、限幅、脉冲式前进 |
| 算力/内存 | 205：8×A55，persond 995 MB / 1.3 核，avail 11 GB；204：48 核 Xeon，余量充足 | 单机版需控增量（≤0.6 核）；服务器版无压力 |
| 前端 | MJPEG `<img>` 显示，已有 ARM/档位/急停/摇杆体系 | 叠加 canvas 即可做框选与目标框绘制 |

## 3. 关键技术选型

### 3.1 目标锁定

**点击框选（主路径）**：`camImg` 上覆盖 canvas，点击坐标换算为归一化坐标 → 前端调 `/api/track/select {u,v}` → 后端取当前帧检测框，选中"包含该点且面积最大"者；无包含则退化为"中心距最近"。返回 `track_id` 与首帧框，前端立即画锁定框。

**手势锁定（辅路径）**：新增 **YOLOv8n-pose**（ONNX，~13 MB）仅在前视 5 Hz 运行，规则：
1. 某人手腕关键点高于同侧肩部（举手过肩）→ 候选；
2. 持续 ≥0.6 s（3 帧确认，防误触）；
3. 候选多人时取**框最大者**（最近）；
4. 仅在进入"手势待命"状态时生效（前端点"手势锁定"按钮后 30 s 窗口，避免日常举手误触发）。

**手势解除**：双手交叉于胸前（两腕中点低于双肩中线且腕间距 < 0.5×肩宽）持续 1 s；或双手举过头顶 1 s。两者与锁定手势区分明确。**按钮结束恒为 P0 必做**，手势解除作为增强。

> 备选：MediaPipe Hands/Pose —— Python 端在 aarch64 无官方良好 wheel，且模型链路更重，不选。NPU（RKNN int8，15–30 ms/帧）留作 P4 加速项。

### 3.2 跟踪算法

单目标、近距、人数少的场景下不需要复杂 ReID：

```
检测（每帧 640 YOLOv8n，8–10Hz）
   └─> 关联：与上一帧目标做 IoU（门限 0.3）+ 中心距（<0.25 画面宽）匹配
         ├─ 匹配成功 → 更新目标状态（框 + 中心速度 EMA）
         └─ 匹配失败 → coasting：按速度外推 ≤1.5 s（画预测框，控制照常）
                          └─ 超时 → 目标丢失 → 停车 + 提示"目标丢失"
   └─> 重捕获（P2）：丢失后在预测区域以大 conf 阈值重检；仍无则用左/右视检测确认目标在侧方
```

- 不用 KCF/CSRT（外观漂移、遮挡后不可靠）；
- 不做全库 ReID（成本高、收益低）；
- 每帧只保留目标框 + 速度，状态极小，便于 10 Hz 稳定运行。

### 3.3 控制律（图像视觉伺服）

误差定义（归一化，画面宽 W、高 H）：

```
e_x = (cx_target − W/2) / (W/2)          # 横向，正=目标在右
e_h = (h_ref − h_target) / h_ref          # 距离，h_ref≈0.45H（约 1.8~2 m）
```

转向（主回路，连续量）：

```
死区 |e_x| < 0.05 → yaw = 0
yaw_cmd = clamp(Kp_y·e_x + Kd_y·ė_x, −0.25, +0.25)   # 跟踪模式限幅（低速档上限的 ~65%）
Kp_y 左/右分设（右侧转向增益 ×0.8，补偿实测不对称）
```

前进/后退（次回路，脉冲式）：

```
若 h_target / H > 0.70  → 过近：停 1 s + x=−0.15 脉冲 0.3 s
若 e_h > 0.15           → 前进脉冲：x=+0.16（低速档）持续 0.25 s，随后 0.35 s 发零（规避 0.15 m/s 步速地板）
若 e_h < −0.15          → 后退脉冲：x=−0.16，0.25 s / 0.35 s
否则                     → x=0
```

工程细节：
- 输出 8 Hz 更新 `NAV_CMD`，`nav_loop` 20 Hz 续发；>0.3 s 未更新自动归零（现有机制即失联保护）；
- 误差做 3 帧中值滤波 + EMA(0.4) 抑制检测抖动；
- 组合工况角速度衰减 20–26% → 增益按 1.25 倍预补偿上限，但不超过限幅；
- 刹停惯性 1.5–2 s → 退出/丢失时连续发零 ≥1.5 s（`nav_loop` 已实现，跟踪退出需保持 ARMED 状态让其生效）。

### 3.4 安全约束（两版通用）

| 项 | 规则 |
|---|---|
| 使能 | 必须 ARM；未 ARM 时跟踪仅"看"不动 |
| 急停 | `/api/estop` 优先级最高：清跟踪会话 + 归零 + 撤 ARM |
| 互斥 | 跟踪激活时前端方向键盘/摇杆置灰（后端亦拒绝 `/api/nav`，返回 409） |
| 限速 | yaw ≤0.25（≈0.3 rad/s）、x ≤0.16（≈0.3 m/s） |
| 断线 | 前端心跳 5 Hz 写 `NAV_CMD`；页面关闭 >0.3 s 自动归零 |
| 超时 | 单次跟踪最长 10 min，到时自动结束 |
| 丢目标 | coasting 1.5 s → 停车 → 3 s 未恢复自动结束会话 |
| 近距 | 框高 >0.70H 视为 <1 m：停车并后退脉冲，再近则退出 |

## 4. 方案 A：单机版（应用在本体 103，推荐主实现）

```
浏览器 ──点击/手势──> app.py: /api/track/*
                        │
                        ├─ TrackingEngine（新线程，8Hz）
                        │    ├─ 取帧：复用 CAM 总线 video4（960w/15fps JPEG）→ cv2.imdecode
                        │    ├─ 检测：YOLOv8n 640（独立 ort session，4 线程）
                        │    ├─ 手势：YOLOv8n-pose 640（仅手势模式，5Hz，按需加载）
                        │    ├─ 关联/coast → 目标框 + 速度
                        │    └─ 控制：e_x/e_h → NAV_CMD（TRACK 源，限幅 ±0.25/±0.16）
                        └─ nav_loop 20Hz → /STEER → DDS → NOS 106
```

- **新增/改动**：`backend/app.py` 加 `TrackingEngine` + 5 个接口 + TRACK 源优先级；`frontend/index.html` 加 canvas 覆盖层、跟踪面板、状态显示；模型文件 `models/yolov8n-pose_640.onnx`（约 13 MB）。
- **接口草案**：

| 方法 | 路径 | 入参 | 出参 |
|---|---|---|---|
| POST | `/api/track/start` | `{mode: "click"\|"gesture"}` | `{ok, session}` |
| POST | `/api/track/select` | `{u, v}`（0–1 归一化） | `{ok, track_id, box}` |
| GET | `/api/track/state` | — | `{state: searching\|locked\|lost\|stopped, box, e_x, e_h, fps, age}` |
| POST | `/api/track/stop` | `{reason}` | `{ok}` |
| GET | `/api/track/overlay` | — | 当前框列表（canvas 绘制用，10 Hz 轮询） |

- **资源增量**（基于 2026-11-27 实测基线）：跟踪激活时 +0.3~0.6 核、+150~250 MB；手势模式额外 +80~120 MB（pose 模型）；空闲 0。
- **与 persond 的关系**：跟踪激活时把前视那一路检测临时降到 1 fps（`switches.json` 已支持单路开关/降频），避免双份推理叠加；跟踪结束自动恢复。
- **延迟预算**（端到端）：相机 66 ms + 总线/JPEG ~100 ms + 推理 42 ms + 关联/控制 25 ms + DDS/机体响应 ~200 ms ≈ **0.45–0.6 s**。
- **优点**：断网可用；环路最短；与现有本机化架构天然一致。**缺点**：A55 算力紧，跟踪期间 persond 需降频；pose 手势模型较重（P4 可上 NPU）。

## 5. 方案 B：服务器版（应用在 204）

```
浏览器 ──> 204: app.py (/api/track/*)
              ├─ TrackingEngine（x86，15Hz 可跑，可上 pose+轻量 ReID）
              ├─ 取帧：RTSP rtsp://<ROBOT_IP>:8554/video4（公网回传）
              └─ NAV_CMD → zenoh-bridge-dds → frp → 205 → /STEER → 106
```

- **架构差异**：检测与控制在 204，指令经 zenoh/frp 回传；复用服务器版现有 `S10Bridge` 发布路径，运动链路零改动。
- **延迟预算**：RTSP 回传 100–300 ms + 推理 15 ms + 指令回程 100–300 ms ≈ **0.3–0.8 s（抖动大）**。
- **控制参数适配**：增益降 30–50%、死区放大到 0.08、输出频率 5 Hz、加一阶低通（τ≈0.2 s）；增加链路健康门限（RTT >400 ms 或丢包 → 自动降速/退出）。
- **资源增量**：204 侧 +0.2–0.5 核 / +200 MB（x86 无压力）；板侧零增量。
- **优点**：算力充裕（可跑更强模型、多目标、录像回放调试）；升级集中。**缺点**：强依赖公网链路，断网即失效；延迟抖动直接影响居中的平稳度（容易出现过冲/振荡）。
- **定位**：作为兼容实现与调试/评估平台；**现场交付以单机版为主**。

## 6. 两版对比

| 维度 | 单机版（A） | 服务器版（B） |
|---|---|---|
| 端到端延迟 | 0.45–0.6 s | 0.3–0.8 s（抖动大） |
| 控制频率 | 8 Hz（检测）/20 Hz（下发） | 5 Hz（检测）/20 Hz（下发） |
| 板侧资源增量 | +0.3–0.6 核 / +150–250 MB | 0 |
| 云侧资源增量 | 0 | +0.2–0.5 核 / +200 MB |
| 断网可用 | ✅ | ❌ |
| 模型上限 | 640 YOLOv8n + pose（可 NPU 加速） | 可上 1280/pose/ReID/多目标 |
| 居中平稳度预期 | 好（短环） | 一般（长环+抖动） |
| 实施工作量 | 中（app.py 内嵌 + 前端 canvas） | 中（同代码，参数分版 + 链路门限） |

**结论**：同一套 `TrackingEngine` 代码，通过环境变量分叉（`S10YK_TRACK_SRC=local|server`、`S10YK_RTSP_BASE`、增益与频率参数），两版共用；单机版为交付主线，服务器版保留同等功能用于回滚与调试。

## 7. 分阶段实施计划

| 阶段 | 内容 | 验收 |
|---|---|---|
| P1（1–2 天） | 点击框选 + 单目标跟踪 + **仅转向**伺服 + 按钮结束 + 安全兜底 | 锁定后 5 s 居中（<10% 偏差）；丢目标 1.5 s 停 |
| P2（1 天） | 距离保持（脉冲控制）+ 过近保护 + 左右视重捕获 + 状态 UI | 1.5–2 m 保持，误差 <0.4 m；遮挡 2 s 内恢复 |
| P3（1–2 天） | 手势锁定/解除（pose 模型 + 规则 + 3 帧确认） | 举手 0.6 s 锁定成功率 >90%（白天室内），误触发 <1 次/10 min |
| P4 | 垂直位置标定、增益整定、NPU 加速评估、现场调参 | 走动跟随平滑无过冲 |

## 8. 风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| 最小步速地板 0.15 m/s | 近距无法微调，易"冲一下停一下" | 脉冲式前进 + 死区；近距离只转向不前进 |
| 转向左右不对称（+0.098/−0.154） | 居中偏向一侧 | 左右分增益（右侧 ×0.8~0.85），实测整定 |
| 组合工况角速度衰减+抖动 | 边走边转时摆动 | 优先"先转后走"；必须同时时降增益 |
| 刹停惯性 1.5–2 s | 停不稳 | 退出/丢失连续发零 1.5 s（现有机制） |
| 遮挡/多人交叉 | 跟错人 | IoU+中心距门限、coast、重捕获；P2 加左右视确认 |
| 手机端 MJPEG 延迟 | 点击位置与实时画面差 0.3–0.8 s | 后端以"最新帧"重选目标，前端回显锁定框确认 |
| 手势误触发 | 日常举手导致误锁 | 需进入手势待命态 + 3 帧确认 + 仅最近者 + 必须 ARM |
| 算力冲突（单机版） | persond + 跟踪叠加 | 跟踪期间前视检测降 1 fps；必要时 640 模型 |
| 安全 | 误动作 | 急停/断线归零/限速/超时/互斥，全部 P0 |

## 9. 待确认（评审问题）

1. 手势集合：锁定=单手举起过肩？还是双手举起？（建议单手举过肩，解除用双手交叉）
2. 距离目标：1.5 m 还是 2 m？（决定 h_ref）
3. P1 是否需要"边走边跟"（x+yaw 同时），还是先只转向？
4. 点击交互：单击选中 vs 拖框选择（建议单击，多人时弹出候选框）
5. 是否允许自动后退（目标突然靠近时）？还是只停车提示？
6. 交付优先级确认：单机版先上，服务器版同步实现但延后验证？
