# 双向对讲下行改造：chunked 长流 → 短请求轮询（2026-11-26，v3.5.7）

## 一、现象（v3.5.6 修复 start 超时后的下一层问题）

- 对讲能正常开启了（"无法开始：Failed to fetch" 消失）。
- **上行正常**：狗侧能听到人声（上行 597KB/20s，符合 32KB/s 理论值）。
- **下行失败**：手机听不到狗端声音，状态栏显示下行仅 86KB。
- 20 秒后对讲自动断开（watchdog `no-listener` 正常收麦——因为下行流断了，无消费者）。

## 二、定位

**86KB ÷ 1280B/帧 ≈ 67 帧 × 40ms ≈ 2.7 秒 PCM**。即 20 秒里 chunked 下行长流只成功传了约 2.7 秒的数据就断了，之后手机无音、后端 `streams=0`，21 秒时 watchdog 收麦。

这和 v3.5.6 的 start 超时是**同一类根因**：**公网 HTTPS 链路对长连接不友好**——
- `/api/talk/start` 等首帧 3s → 被断（v3.5.6 已修）；
- `/api/talk/pcm` chunked 长流 → 传 2.7s 后被掐断（本次）；
- `/api/shout/pcm` 全是短 POST → 一直稳定。

## 三、修复方案：下行改短请求轮询（与已验证可用的喊话同模式）

### 后端 `backend/app.py` —— `/api/talk/pcm` 重写

- 删除 chunked 长流实现；改为：每次请求阻塞凑满 `ms` 毫秒（query 可传，默认 200，限 40~500）的 PCM 后，以 `Content-Length` 立即返回 `application/octet-stream`。
- 不发 `Connection: close`：HTTP/1.1 + Content-Length 下浏览器可复用 TLS 连接（实测握手开销吃掉约 1/3 吞吐：加 close 时 21KB/s，去掉后 curl 场景 25.7KB/s，浏览器 keep-alive 更接近理论值）。
- 复用 `talk_stream_begin/end` 包住每次请求：watchdog 的"无消费者 20s 收麦"逻辑不变（轮询间隙 <1s，不会误触发；流真断了则正常收麦）。
- 无数据返回空体，前端继续轮询；会话结束返回 409，前端正常退出。

### 前端 `frontend/index.html` —— `talkDownlink()` 重写

- 删除 ReadableStream 长读；改为串行 `while` 轮询 `GET /api/talk/pcm?ms=200`。
- 单请求 5s AbortController 兜底超时；网络抖动提示"下行抖动，重连中…"并 300ms 后重试，不清场。
- `409`（后端会话已收麦）正常退出；`TALK_ABORT.abort()`（主动挂断）路径兼容。
- 收到的字节直接走 `talkPlayPcm()` 时间戳排队播放（该函数本来就支持批式数据，掉队自动跳当下重建缓冲）。

## 四、验证

| 项 | chunked（修复前） | 轮询（修复后，curl 每请求独立 TLS） |
|---|---:|---:|
| 下行吞吐 | 86KB/20s ≈ **4.3KB/s**（断流后 0） | 259840B/9.89s ≈ **25.7KB/s**（50 次全成功） |
| start 响应 | — | 0.017s，ok=true |
| 会话状态 | streams 恒 0 | 采集正常，停止干净 |

浏览器内 fetch 会复用 TLS 连接，实际吞吐将更接近理论 32KB/s；即使短暂欠速，`talkPlayPcm` 的缓冲重建逻辑保证卡顿而非静音。
