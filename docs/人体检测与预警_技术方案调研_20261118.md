# 人体检测与预警_技术方案调研（REQ-047，2026-11-18）

> 需求：通过机器狗本体的 4 路摄像头做人体检测，检测到人体后保存当前画面并预警。
> 本文为方案调研与选型，未实施。探查时间：2026-11-18 11:15~11:20（全部为本机实测）。

## 1. 现状实测（选型依据）

- 4 路摄像头输出：`rtsp://10.21.33.103:8554` 的 video0/2/4/6（机尾前视/机头后视/左右视，见 D-033 标签修正），**H.264 1024×576@30fps**，由 103 板上 8554 端口 RTSP 服务提供（`ss` 确认监听）。

### 1.2 三台算力平台对比（实测数据）

| 平台 | 算力 | 内存 | CV 环境 | 当前负载 | 结论 |

### 1.3 NPU 状态（103 板，实测）


## 2. 方案对比

### 方案 A：204 服务器 CPU 推理（⭐ 建议一期方案）

```
4路RTSP(103) → ffmpeg/OpenCV拉流 → 204: onnxruntime + YOLOv8n(仅person类) 
  → 命中: 抓拍JPEG存盘 + /api/status 加预警字段 + 控制台横幅 + 语音播报(sayd)
```

- **优点**：
  1. 48 核 Xeon 跑 YOLOv8n@640 绰绰有余（单帧 ~30ms/核，4 路 × 5fps 仅占 2~3 核）；
  2. 拉流链路零新增（复用控制台同源 RTSP）；预警直达后端，前端/语音通道全是现成的；
  3. 部署只在 204（装 `opencv-python-headless` + `onnxruntime`，免 GPU 免编译），不碰狗本体、不影响运动/定位；
  4. 抓拍存 204 大盘，存储管理方便，控制台回看零成本。
- **缺点**：依赖 204→103 链路；狗脱站/断链时检测失效（但此时控制台视频同样失效，预警本身也失去意义）；时延 ~0.5s 级（够用）。

### 方案 B：103 板 NPU 推理（⭐ 建议二期演进）

```
本地video节点/GST → RKNN int8 YOLOv8n(6TOPS NPU, 单帧 15~30ms) → DDS/HTTP 上报 204
```

- **优点**：离线可用（断链仍能检测）、单路 30fps 实时、功耗低；
- **代价**：①需用 rknn-toolkit2 在 PC 上把 ONNX 转 RKNN int8 并校准；②需确认 renderD 节点权限与 librknnrt 运行库部署；③预警要新建 103→204 上报通道；④与厂商节点共存需隔离 CPU/内存（BBS 已占核 6/7 的教训）。
- 定位：一期方案 A 稳定后，将检测器"下沉"到 103 即为二期。

### 方案 C：106 板推理 — ❌ 否决（load 9.28，定位精度对算力敏感，BBS 重定位刚出过超时问题）。

## 3. 模型与检测策略选型

| 项 | 选型 | 理由 |
|---|---|---|
| 检测模型 | **YOLOv8n / YOLO11n**（COCO 预训练，只取 person 类，conf≥0.5） | 4M 参数，行人/人体场景成熟，ONNX/NPU/RKNN 全生态支持；无需自己标注训练 |
| 输入分辨率 | 640×384（letterbox，近原生 1024×576） | 小目标（远处人体）够用；如漏检可升 960 |
| 帧率策略 | 每路 **2~5 fps 抽帧检测**（跳帧，不逐帧） | 人体移动慢，2fps 捕获率 >99%；大幅省算力 |
| 4 路并发 | 单进程 4 线程，204 上合计 <3 核 | — |
| 抓拍策略 | 命中即存：**检测帧 + 命中前 1s 环形缓冲 5 帧**（JSON 记录 cam_id/时间/置信度/框坐标） | 事后可回放进入过程 |
| 去重 | **同路冷却 5~10s**（持续出现不重复报警），新目标复报 | 防刷屏 |
| 存储管理 | `/opt/s10yk/alerts/person/{cam}/{yyyymmdd}/`，保留 7 天自动清理，单日上限 | 防爆盘 |

## 4. 预警通道设计（全部复用现有设施）

1. **控制台**：`/api/status` 新增 `person_alert` 字段（最近一次：时间/摄像头/置信度/抓拍图 URL）；前端状态卡上方弹红色横幅 + 声音提示，点击看抓拍图（经 `/api/cam/alerts` 鉴权下发）。
2. **语音播报**：复用 sayd 链路，播报「注意：摄像头 N 检测到人员」（沿用 D-027/D-038 的通道与开关修复）。
3. **抓拍回看**：控制台新增"预警记录"入口（列表 + 大图），数据源即存储目录。

## 5. 风险与待确认项

| 项 | 说明 | 消解 |
|---|---|---|
| NPU renderD 权限 | rknpu 走 `/dev/dri/renderD*`，需确认 user 可读写 | 一期不依赖 NPU，实施时验证 |
| 4 路拉流带宽增量 | H.264 4 路 ~8~12 Mbps，走 204→103 有线（ens16f0 已承载 66Mbps，余量足） | 低风险 |
| 链路断 = 检测断 | 方案 A 固有 | 二期 NPU 下沉解决 |
| 隐私合规 | 人体抓拍涉及在场人员肖像 | 建议现场张贴告知；抓拍仅存本地 7 天 |
| 与厂商栈共存 | 103 上不跑新进程（一期），204 上独立 venv | 一期无接触 |
| 夜间/逆光漏检 | YOLO 常见弱点 | 二期可换低照度增强模型或红外补光验证 |

## 6. 实施分期建议

- **一期（预计半天）**：204 装 `opencv-python-headless + onnxruntime + yolov8n.onnx`（ Ultralytics 官方导出 person-only）；后端 `app.py` 加检测线程（4 路×3fps）+ 抓拍存盘 + `/api/status.person_alert` + 前端横幅；语音播报开关。真机验证：人走到各机位前 → 各路命中 → 抓拍 + 横幅 + 播报。
- **二期（验证后）**：rknn-toolkit2 转 int8 → 103 NPU 部署 → 断链场景可用；增加 4 路同显检测框预览。
