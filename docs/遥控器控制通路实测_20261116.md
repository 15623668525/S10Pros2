# 遥控器控制通路实测：狗能走，走的是 STEER 不是 NAV_CMD

**日期**：2026-11-16 20:56–20:58（120 s 连续采集）
**目的**：用遥控器（网络连接 10.21.33.103）实测前进/后退，验证"控制台下发运动指令无效"到底是**链路不通**还是**选错接口**
**操作方式**：现场用遥控器前后各推多次，每次 2–3 s，中间停顿；狗接电源线充电

---

## 一、一句话结论

**遥控器能让狗正常前进/后退，通路是 DDS 话题 `/STEER`（`drdds/msg/Steer`，`data.x` 为前后量），与 `/NAV_CMD` 无关。**

这从反面证实了 OPS-36 的判断：不是网络/链路问题，是**控制台一直在往一条对机器人无效的话题上发指令**。

---

## 二、实测时间线（唯一可靠判据 `MOTION_INFO.vel_x`）

| 相对时间 | `/STEER` 的 x | `vel_x` (m/s) | gait / state | 现场动作 |
|---|---|---|---|---|
| 0–40 s | 无数据（静止不发） | 0.0000 | 0 / 0 | 狗趴着 |
| 40 s | **0.000 → 0.750** | 0.0000 | 0 / 0 | 推杆（尚未站起） |
| 42 s | — | 0.0000 | 0 / **1** | 站立完成 |
| 44 s | — | 0.0000 | 0 / **17** | 进入运动态 |
| 46 s | — | 0 → **+0.0269** | **4097** / 17 | 步态自动切常规 |
| 48 s | — | 0 → **+0.3269** | 4097 / 17 | **前进** |
| 52–100 s | **+0.340 / −0.570 交替** | **−0.4819 ~ +0.4215** | 4097 / 17 | 前后反复推杆 |

**因果链**：`STEER.x` 正负交替 → `vel_x` 同向跟随，正负一致，滞后 < 1 s；静止期两者同时归零。

---

## 三、关键事实

1. **`/STEER` 是事件型话题**：只在推杆时发布，松手后不再发（不是 10 Hz 常发）。所以"静止时看不到 STEER 帧"是正常现象，不代表通道断开。
2. **`/STEER` 与 `/HANDLE_STEER` 内容完全一致**（帧数、min/max 逐项相同）→ `/STEER` 是操纵杆原始量，`/HANDLE_STEER` 是同一份输入的镜像/转发。
3. **`/REAL_STEER` 在 120 s 内 0 帧**，但 `ros2 topic info` 报 3 个 publisher → 该话题存在但本场景下不活跃（QoS 不匹配或未启用），不能作为控制入口。
4. **`/ROBOT_CMD_INSTRUCTION` 0 帧**，本次遥控不经过它。
5. **发布者名前缀均为 `_CREATED_BY_BARE_DDS_APP_`**（厂商用裸 DDS SDK，非 rclcpp），`ros2 node list` 只能看到 `/s10yk_bridge`、`/traversability_estimation_node`、`/ubeacon_driver`，看不到遥控接收节点。
6. **`/STEER` 当前 2 publisher / 4 subscription**，`/MOTION_STATE` 2 publisher。
7. **站起 → gait 自动 4097** 再次验证（OPS-36 部署的 `stand_sequence()` 修复生效）。

## 四、与 NAV_CMD 的对比（为什么之前必然失败）

| 项目 | `/NAV_CMD` | `/STEER` |
|---|---|---|
| 实测是否驱动狗 | **否**（4 种步态组合下 `vel_x` 恒 0） | **是**（`vel_x` 达 ±0.48） |
| 生效前提 | 文档注明"仅导航模式下生效" | 无前提，直接生效 |
| 遥控器是否使用 | 否 | **是** |
| 量纲 | m/s（物理速度） | 归一化操纵杆量（观测 −0.57 ~ +0.75，疑似 −1~+1） |

**结论**：控制台继续用 NAV_CMD 无论怎么调都不会有效果。ASDU 真实轴控制（方案 B）也**不是唯一出路** —— 直接发 `/STEER` 是更短、更已被现场证明可行的路径。

## 五、下一步建议（按性价比排序）

### 方案 S1（推荐，最短路径）：控制台改发 `/STEER`
- 后端已有 `drdds/msg/Steer`（`/opt/s10yk/install/drdds/.../msg/_steer.py` 存在），零新依赖。
- 只需把 `publish_nav_cmd()` 换成 `publish_steer(x, yaw)`。
- **必须先做量纲标定**：分档发 `x = 0.02 / 0.05 / 0.10`，读 `vel_x`，拟合成 `vel_x = k · x`，确定 k 与饱和值。在此之前**不得直接发 0.3 以上的 x**（本次观测 x=0.75 已对应 0.33 m/s，若误按 m/s 理解会超速）。
- 安全兜底：发完必须补发 `x=0`，并保留软件限速（建议 `|x| ≤ 0.10` 起步）。
- 待确认：遥控器是否会在空闲时持续发 0 覆盖我们；若会，需要先断开遥控。

### 方案 S2：ASDU 真实轴控制（原方案 B）
仍可作为长期正解，但要实现 TLS 客户端 + 16 字节头 + JSON ASDU，工作量大，且本次实测证明 S1 已够用。

### 方案 S3：ASDU 切导航模式 + NAV_CMD
需要 ASDU，还要依赖"导航模式"语义，链路最长，收益最低。

# 八、注入标定结果（2026-11-16 21:37–21:45，狗已移至开阔地）

## 8.1 前置状态

`h=0.387 / state=17 / gait=4097`（全站姿、运动态），无需再走站立序列。所有实验 20 Hz 持续下发，段间发零。

## 8.2 前后通道 `data.x` —— **有效**

| x | vel_x 稳态 (m/s) | 峰值 |
|---|---|---|
| 0.03 | **+0.1510** | 0.1524 |
| 0.05 | **+0.1956** | 0.1965 |
| 0.10 | **+0.2439** | 0.2472 |
| 0.15 | **+0.2944** | 0.2999 |

**结论**：
- 线性拟合 **`vel_x ≈ 0.115 + 1.19 · x`**（截距来自最小步速）。
- **低速不可控**：x=0.03 就已经 0.151 m/s。存在约 **0.15 m/s 的"最小步速地板"**，x 再小也不会更慢（待补测 x<0.03 确认是否为硬地板）。
- **刹停需要时间**：发 0 后 1.0 s 仍残余 0.013 m/s，约 1.5–2 s 才归零。控制台必须"松手即发零 + 保持 ≥1.5 s"，且急停要靠 `MOTION_STATE=2`（会趴下，见 OPS-36）。

## 8.3 转向通道 `data.yaw` —— **有效**

| yaw | vel_yaw 稳态 (rad/s) | 说明 |
|---|---|---|
| +0.12 | **+0.0984** | 逆时针 |
| −0.12 | **−0.1541** | 顺时针 |

**结论**：`data.yaw` 是转向入口，符号正=逆时针、负=顺时针（与文档 `vel_yaw` 定义一致）。但**正负不对称**（0.098 vs 0.154），且归零后 0.8 s 内仍有 −0.055 rad/s 残余 → 转向阻尼较大，控制台需加"反向微脉冲"或延长归零保持。

## 8.4 左右平移 `data.y` —— **无效**

| 输入 | vel_y 实测 |
|---|---|
| y=+0.12 | −0.0025 |
| y=−0.12 | −0.0016 |

**结论**：`STEER.data.y` 不被机器人读取（恒为噪声级）。`data.z` 同样无效（vel 全零、高度无变化）。

> **左右平移目前没有可用通道。** 四足侧移若必须实现，只能靠"转向 ±90° + 前进"组合，或另找厂商话题。遥控器本身可能也没有横移键。

## 8.5 安全观察

- 遍历 `z=0.12` 时高度、速度均无变化，未触发姿态异常。
- 转向试验时高度在 0.375~0.393 间波动（正常步态起伏，<±0.02）。
- 全程 `state=17 / gait=4097` 未掉，收尾后 `vx=vy=0`，狗稳定站立。
