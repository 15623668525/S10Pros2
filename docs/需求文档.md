## 2. 需求详情

### REQ-001 远程遥控应用（前后端）

- 后端：机器人本体（RK3588 NOS）常驻服务，systemd 管理，开机自启、异常自恢复。
- 前端：单文件网页，支持手机触屏与 PC 鼠标。
- 约束：板上无外网 → 后端不得依赖需联网安装的第三方包。

### REQ-002 运动控制

| 功能 | 实现 | 备注 |
|---|---|---|
| 站立 | `POST /api/motion/state {state:1}` | v1.3 起为「起立(1) → 自动补 RL(17)」序列 |

安全要求：默认未使能，且未使能时后端对 `/STEER` 完全静默（不干扰遥控器）；前端 `window` 级松手/失焦兜底归零；后端松手后连发零 1.5s（实测刹停惯性 1.5~2s）。速度范围见 REQ-021。

### REQ-016 硬件共用环境：优先话题，直驱硬件必须"用完即还"（v2.4 新增）

**背景**
- 机器人是**共用环境**：106（应用/ROS2）与 103（运控 + 声卡）同机不同容器，厂商音频节点与我们的播报共用同一声卡播放子设备。
- 审计结论（《实现方式审计_话题与硬件.md》）：11 项功能已走 ROS2 话题；3 项直驱硬件——自定义语音播放/停止（高抢占）、音量读写（低风险，只动混音器）、麦克风采集（不可用）。

**要求**
1. 能走话题的一律走话题（运动控制、状态读取、预置音效均如此）。
2. 必须直驱硬件的项，不得长期占用：用前打开、用完立即释放，异常退出也不得残留句柄。
3. 直驱项若阻塞了厂商功能，需给出明确的规避/让路机制，并在文档中记录证据。

**落地（v2.4）**
- 自定义语音：103 常驻 `sayd`（systemd），按需 `open`、`STOP`/断链立即 `close`、空闲 1.2 s 自动释放；停止 ≤100 ms 生效。
- 预置音效：统一 `play_preset()`（STOP → FORCE → 无回执则重试），避免被厂商调度器卡死项吞掉。
- 音量：无话题可用（`/AUDIO/CONFIG` 仅切音色），保留 `amixer`；因其只操作混音器控件、不打开 PCM 流，巡检间隔放宽到 60 s。

**已知无法话题化的部分（接口能力限制）**
- `/AUDIO/COMMAND` 无"播放任意文件"通道；`audio.yaml` 不热加载；节点资产为该容器私有副本。
- 结论：自定义语音在厂商开放相应接口前，只能做到"零残留 + 播完即还"。

**验收**
1. `/api/audio/play`（自定义）→ 103 `card0` RUNNING；`/api/audio/stop` → 0.8 s 内 `closed`、无 `aplay` 残余进程。
2. 循环播报期间厂商系统提示音可正常插播。
3. 人为让调度器卡死后，预置音效仍能播（自愈重试生效）。

**交互细节**
- 点「高台」再点一次 → 回 `0x1001` 基础（与官方遥控器行为一致），否则进了高台就没有退出按钮。

### REQ-039 一键喊话升级为实时对讲（v3.0 新增）

**目标**：把「一键喊话」从**录完即播**（松手后整段上传再播）升级为**边说边播**，说出口后约 0.6~0.9s 即出声，不再等整句录完。

**链路**：按住 → 先 `getUserMedia` 取麦（授权框不应让 sayd 空占声卡）→ `POST /api/shout/start` 建会话 → AudioWorklet 每 100ms 产一片 3200B PCM → **串行** `POST /api/shout/pcm` → sayd 收到即写 aplay → 松手**先排空队列**再 `POST /api/shout/stop`。

1. **串行保序**：同一时刻只有一个上行请求在飞。并发 POST 会让多线程同时写 sayd socket，帧字节交错 → 碎音/爆音。
2. **自适应合批**：单次最多合并 4 片（400ms）。网络慢时排队片自然变多、批量变大，请求数下降而吞吐仍跟得上实时速率。
3. **队列上限 15 片（≈1.5s）**：超出即丢最旧一片并计数，宁可掉字也不让延迟越积越大；提示条实时显示「对讲中 x.x s」与丢片数。
4. **会话自愈**：收到 409（会话被看门狗/其它音频入口终止）时自动重建一次会话并重发该批，句子不会断在那里。
5. **代次保护**：`SHOUT_GEN` 计数；松手收尾（排空→stop）途中若又按下新会话，旧收尾直接放弃，不会误停新会话。
6. **指针捕获**：`setPointerCapture` + 不再监听 `pointerleave`，手指滑出按钮仍继续对讲，只有松手/取消才结束。
7. **后端配套**：HTTP/1.1 keep-alive（否则每 100ms 一片都要重做 TCP+TLS 握手）、`timeout=65` 回收空闲连接、`disable_nagle_algorithm`；sayd socket 设 `TCP_NODELAY`（Nagle 会给小片攒出额外延迟）；`SHOUT_TX` 锁串行化写帧；空闲判停 3s→5s、单次上限 60s→120s（适配手机网络抖动与长句）。

**验收**：见 OPS-63。服务端实测——HTTP/1.1 复用连接（`connects=0`、0.25ms）；30 片×3.2KB 按 100ms 节奏推完 3.03s、`bytes=96000` 精确对齐、单请求延迟中位 1.0ms、看门狗未误杀；MJPEG 与明文端口回归正常。**真机听感（延迟/丢字/尾音）仍需现场按住说话确认**。

- 互斥：`/api/audio/{play,say,stop}` 与 `say_wav()` 现在同时停 shout 与 talk；对讲自身 start 前先停播报。
- 回声：手机外放声可能被机器人麦再采回来（回授）。已用浏览器 AEC + 下行增益 0.9 缓解，建议戴耳机或调低媒体音量。

**验收**：见 OPS-67——首帧 0.6s 内到达；下行 4s 126976B（≈32KB/s 实时速率）；杀采集进程 → `preempt:1` 且会话自愈续采；占麦 12s 后 start → `ok:false, preempt:4(1+3 重试)`，释放后 start `ok:true` 且 `preempt_total` 保留；stop 后无 arecord/ssh 残留、`pcm0c=closed`；幂等 start 不再死锁（D-035）；HTTP/HTTPS 200。

### REQ-042 休眠/唤醒两态切换（v3.1 新增，D-039 衍生）

**背景**：OPS-74 确认运控失效+趴下+视频 404 是机器人进入厂商休眠模式（手柄 APP 可见）；控制台无法主动进出休眠，也无法识别，用户要求增加切换按钮。

**接口**：`POST /api/motion/sleep {sleep:bool}` → `{ok,sleep}`；`/api/status.motion` 新增 `sleep`（请求标志/已确认）、`suspect`（疑似厂商休眠：state=0 且 h<0.10）。

**实现取舍**：厂商协议**无独立休眠指令**——ASDU 运动状态转换表有 `0x1001 阻尼趴下`（指南 p10），但 ROS2 `/MOTION_STATE` 话题只支持 0/1/2/4/17（p56-57），真机下发 0x1001 无效（站立纹丝不动）。故休眠走话题可达的等效序列 **4(趴下)→贴地→2(关节阻尼)**；唤醒复用 `stand_sequence` 1→17→自动挂步态。进休眠同时撤 ARM、清零速度、锁十字盘。

**前端**：「运动控制」标题行档位按钮右侧加 `#sleepBtn`（🌙休眠 / ☀️唤醒），橙底高亮表休眠中；休眠中十字盘保持禁用；状态卡「运动状态」在 state=0+贴地时显示橙色「疑似休眠」tooltip 提示用手柄唤醒。按钮状态由 `/api/status` 同步，多端一致。

**验收（OPS-75）**：实测休眠后 h 0.387→0.08、state 17→0，日志 `SLEEP seq: 4→2`；唤醒 4s 回 h=0.387/state=17/gait=4097；前端 CSS 与 JS 语法通过、线上已生效。**局限**：CSV 关节温度列未归零 → 未真正断关节电；不关相机推流、不停厂商栈；与厂商手柄休眠是「物理表现相似、机制不同」，不能互相替代唤醒。

### REQ-043 前进+转向组合控制安全实测（v3.1，配合 UI 改造前置）

**要求**：UI 支持前，先实测低速档 `x=0.16+yaw=0.15` 组合 2s，验证 vx/wz 是否同时响应、是否符合单通道标定。

**结果**：见 `evidence/combo_fwd_turn_20261117.log`（两轮）。vx 稳态 0.297~0.314 m/s 与标定 0.306 吻合；vyaw 稳态 0.135~0.146 比单通道 0.183 低 20~26% 且时序剧烈抖动（含瞬时反向）→ 组合工况角速度被线速度耦合/限幅；转弯半径 ≈2.2 m。同时响应确认、峰值 0.398 m/s 远低于 0.85 阈值、回零 3s 干净。右转组合与敏捷步态组合未测。

### REQ-044 圆形八向方向盘：前进中左右转 + 恢复直行（v3.1.1）

**背景**：REQ-043 实测证实机器人本体支持 x+yaw 组合（vx/vyaw 同时响应），但原十字盘 `.dpad` 用单值 `DPAD_DIR`，一次只能发一个方向，组合无法下发。用户要求重做方向盘，覆盖「前进 / 后退 / 左转 / 右转 + 前进过程中左右转 + 恢复直行」全部状态。

**交互设计**：3×3 十字盘改为 186px 圆形可拖动方向盘 `#wheel`：
- 上/下 = 前进/后退；左/右 = 原地转向；左上/右上 = 前进同时左/右转（另含后左/后右）；
- **不松手从斜向拖回正上 = 恢复直行**（关键状态，无需松手重按）；
- 松手 / pointercancel / 失焦 = 回中停止；键盘 ↑+← 组合，松开 ← 自动恢复 ↑；
- 中心 thumb 实时显示状态文字（前进/前+左/…/停）并跟随拖动；
- `touch-action:none` 只作用于圆盘本身，页面其余滚动不受影响。

**实现**：纯前端 `frontend/index.html`。`WHEEL_VEC` 8+1 档位（±0.6 对齐后端量化）、`wheelDirFromXY()` 按 42% 扇区阈值判 8 向 + 12px 中心死区、`wheelSet()` 一次写 `curNav.x` 与 `curNav.yaw` 并 `sendNav()`；`WHEEL_KEYSET` 实现键盘组合与释放恢复；保留 ARM/休眠锁定与 100ms 保活。后端 `/api/nav` 零改动（本就支持双通道）。

**验收**：8 向映射 + 组合向量 + 恢复序列纯逻辑自测 17 项全通过；JS `node --check` 通过；线上页面新标记全部命中、旧 `data-dir` 0 处；服务 active。未做真机拖动实测（避免无人值守驱动机器人），组合效果沿用 OPS-76 实测凭证。
