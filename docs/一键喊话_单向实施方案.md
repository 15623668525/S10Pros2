# 一键喊话（单向）· 技术方案

> 版本：v1.0　｜　日期：2026-11-17　｜　基线：后端 `app.py` 1358 行 / sayd `remote/sayd.py` 275 行 / 前端 `index.html` 689 行
> 范围：**单向喊话（手机麦克风 → 机器狗本体扬声器）**，不含狗端收音回传；外观暂不考虑；浏览器先只支持 **Chrome**（允许自签 HTTPS）
> 依据：`一键喊话_技术方案调研.md`（含 §11 结合官方资料的补充调研）、`实现方式审计_话题与硬件.md`

## 1. 目标与边界

| 项 | 定义 |
|---|---|
| 做什么 | 手机浏览器点一下开始说话，声音经后端实时/准实时送到机器狗本体扬声器播出 |
| 分几步 | **阶段一「录完即播」**（按住录音→松手播整段）→ **阶段二「实时对讲」**（边说边播） |
| 方向 | 仅手机 → 狗喇叭（单向）。狗端麦克风回传（收音/双向对讲）**不在本次范围**——已实测 `/AUDIO/RECORD_CMD` 崩溃、`arecord` 硬件 busy（调研 §9） |
| 浏览器 | 仅 Chrome（Android / 桌面）。iOS Safari / 微信内置浏览器不支持自签证书下的麦克风授权，明确不支持 |
| 外观 | 本次只做可用 UI（一个大按钮 + 状态文字），不追求版式美观；样式可后续套用现有 `.sw`/`.tab` 风格 |
| 硬件 | 复用本体扬声器 + sayd，不新增外挂载荷。官方 110 dBA 级高声压属外挂"二代多合一"载荷范畴，不在本次 |

## 2. 可复用基础（现状核对，方案之所以可行的依据）

1. **sayd 常驻播放器**（跑在声卡所在板，当前 `SAYD_HOST=<ROBOT_IP>`，端口 18081）：对外 TCP 帧协议 `type(1B)|len(4B)|payload`——
   `F_START=1`（payload=`{"rate":16000,"channels":1}`）、`F_PCM=2`（原始 S16_LE 字节，可任意分片）、`F_STOP=3`、`F_PING=4`；控制帧回 `OK`/`BUSY …`/`ERR …`。sayd 端用 `aplay -D plughw:0,0 -t raw -f S16_LE` 播放，单实例、播完/空闲 1.2 s 即释放设备。
   → **喊话 = 给 sayd 灌 PCM，与现有 `say_wav()` 完全同构，无需改 sayd。**
2. **后端已有推流骨架**：`_say_frame()` / `_say_reply()` / `say_stop()` / `say_wav()`（`app.py` L605–850）。`say_wav()` 已实现"连 sayd → START → 按 3200 B/100 ms 节流发 PCM → STOP"，`SAY_CHUNK=3200` 即 100 ms@16k/mono/16bit。
3. **互斥机制**：`say_stop()` 停 sayd 播放；`BRIDGE.audio_stop(0)` 停 DDS 预置音效（`/AUDIO/COMMAND`）。现有 `/api/audio/play`、`/api/audio/say` 都已按"先互斥再播"处理——喊话沿用同一约定。
4. **接口分发**：`do_POST()`（`app.py` L1211）按 `path` 分支，鉴权 `_auth_ok()`、流量 `_meter_request()` 已统一处理。
5. **部署**：`s10yk-backend.service` 跑在 204，**HTTP 端口 18090**（`S10YK_PORT=18090`），无 HTTPS；`openssl 3.0.13` 可用。

## 3. 总体架构与链路

```
┌──────────────── Chrome 手机 ────────────────┐
│  getUserMedia(麦克风)                        │
│  AudioContext 16kHz mono → Int16 PCM         │
│  ① 录完即播: 攒整段→WAV→POST /api/shout/clip │
│  ② 实时对讲: 每100ms一片→POST .../pcm        │
└───────────────┬──────────────────────────────┘
                │ HTTPS (自签, 18443)
                ▼
┌──────────────── 204 后端 app.py ────────────┐
│  互斥: say_stop() + audio_stop(0)            │
│  喊话会话管理 SHOUT{sock,ev,ts,bytes}         │
│  看门狗: 3s 无数据 → 自动 STOP               │
│  ├ 阶段一: wav落临时文件→复用 say_wav()       │
│  └ 阶段二: TCP → sayd START/PCM/STOP         │
└───────────────┬──────────────────────────────┘
                │ TCP 18081 (S16_LE 帧)
                ▼
┌──────────────── 205 sayd + 声卡 ────────────┐
│  aplay -D plughw:0,0 → 本体扬声器播出         │
└──────────────────────────────────────────────┘
```

两个阶段的差异只在"手机→后端"这一段：**阶段一一次 POST 一整段，阶段二多次 POST 流式分片**；后端→sayd→扬声器完全一致。

## 4. HTTPS 自签证书（Chrome 前置门槛，两阶段共用）

`getUserMedia()` 仅在**安全上下文**可用，HTTP 的 LAN 地址在 Chrome 中必然拒绝；自签 HTTPS 经用户显式信任后 Chrome 视该源为安全上下文，麦克风可用。

1. **生成带 SAN 的证书**（Chrome 自 Chrome 58 起**只认 SAN、不认 CN**；把 IP/域名都写进 SAN）：
   ```bash
   openssl req -x509 -newkey rsa:2048 -nodes -days 825 \
     -keyout /opt/s10yk/certs/key.pem -out /opt/s10yk/certs/cert.pem \
     -subj "/CN=<SERVER_IP>" \
     -addext "subjectAltName=IP:<SERVER_IP>,DNS:s10.local"
   ```
   实际访问用什么地址（IP 或域名），就要把对应项加进 SAN；否则 Chrome 即使信任也会因主机名不匹配拦截。
2. **后端加 TLS 启动能力**（`app.py` L1349 `main()`）：新增 `S10YK_TLS_CERT` / `S10YK_TLS_KEY` 环境变量；配置了就用 `ssl.SSLContext(ssl.PROTOCOL_TLS_SERVER).load_cert_chain()` 包住 `ThreadingHTTPServer.socket`，未配置则维持现有明文行为（不影响 18090 现状）。
3. **监听端口**：保留 18090 明文（现有控制台、拉流、调试不受影响），**新增 HTTPS 实例监听 18443**——通过第二个 `s10yk-backend-tls.service` 用同一份 `app.py` + `S10YK_PORT=18443` + TLS 变量启动，两个实例互不干扰（流量/控制状态各自独立，若需跨实例共享状态则改为同一实例双监听，见 §9 取舍）。
4. **Chrome 信任步骤**：手机/电脑 Chrome 访问 `https://<host>:18443/` → 提示"您的连接不是私密连接" → 点「高级」→「继续前往（不安全）」。此后该源为安全上下文，麦克风弹窗可正常授权。
5. **降级**：若证书信任环节卡住，阶段一支持"在桌面 Chrome 录好 WAV → 上传"作为兜底（调研 §7）。

## 5. 阶段一：录完即播（推荐先落地）

### 5.1 交互
UI 一个大按钮「🎤 按住喊话」：移动端 `pointerdown` 开始录音、`pointerup` 结束并播放；桌面端点击开始/再点结束。录音中显示计时（外观从简）。

### 5.2 前端采集（Chrome）
- `navigator.mediaDevices.getUserMedia({audio:{echoCancellation:true, noiseSuppression:true, autoGainControl:false, channelCount:1}})`；
- `AudioContext({sampleRate:16000})` + `MediaStreamAudioSourceNode` + `AudioWorklet`（降采样/转 Int16；简化实现可用 `ScriptProcessorNode(4096,1,1)`，但已废弃，建议 AudioWorklet）；
- 音频回调把 `Float32` 样本乘 32767 转 `Int16`，累积到数组；松手时组装 **WAV（44 字节头，16 kHz / mono / 16 bit）** 成 Blob；
- `POST /api/shout/clip`，`Content-Type: audio/wav`，body = WAV 字节；
- 状态提示区分「未授权麦克风」「需要 HTTPS」「设备忙」，失败可重录。

### 5.3 后端接口
| 接口 | 方法 | 说明 |
|---|---|---|
| `POST /api/shout/clip` | WAV 二进制 | 落临时文件 → `say_wav()` 播放，返回 `duration_ms` |
| `POST /api/shout/stop` | JSON | 停喊话（`say_stop()`），阶段二也复用 |
| `GET /api/shout/state` | — | 返回 `{active, mode, seconds, bytes}` |

处理要点：
- `do_POST()` 的 `body = self._json_body()` 是按 JSON 读的，**二进制接口需分支**：在读取 body 前判断 `path.startswith("/api/shout/")` 则 `raw = self.rfile.read(int(self.headers["Content-Length"]))`，不走 JSON 解析；
- 校验 WAV 头（RIFF/WAVE、采样率、位深），非法返回 400；限制最大时长（如 60 s）与字节数防滥用；
- 互斥：`say_stop()` + `BRIDGE.audio_stop(0)` 后再播；临时 WAV 固定写 `ASSET_DIR/_shout_tmp.wav`（覆盖式），`say_wav()` 直接读它——无需动态文件名与定时删除；
- 返回值含 `duration_ms`，前端据此显示"播放中…"计时。

### 5.4 延迟
松手 → WAV POST + sayd 起播 ≈ **0.5–1.5 s**，现场喊话可接受。

## 6. 阶段二：实时对讲（阶段一稳定后）

### 6.1 接口（会话式，规避 chunked 解析）
用三个 JSON/二进制接口维护一个喊话会话，避免让 `BaseHTTPRequestHandler` 解析 HTTP chunked：

| 接口 | 方法 | Body | 说明 |
|---|---|---|---|
| `POST /api/shout/start` | JSON | `{rate:16000, channels:1}` | 互斥清理 → 连 sayd 发 `F_START` → 建会话 + 启看门狗；返回 `session` id 或 `ok` |
| `POST /api/shout/pcm` | 二进制 | 每片 3200 B（100 ms）PCM | 会话内按序 `F_PCM` 发给 sayd；更新 `bytes`/`ts` |
| `POST /api/shout/stop` | JSON | — | 发 `F_STOP` + 关连接 + 清会话 |
| `GET /api/shout/state` | — | — | `{active, seconds, bytes}` 供 UI 显示 |

### 6.2 前端
- 复用阶段一的 `getUserMedia` + AudioWorklet；
- 采集回调不再攒整段，改为**每凑够 3200 B 就 `POST /api/shout/pcm`**一次（100 ms 一片）；
- 开始按下 → `POST /api/shout/start`；松手 → `POST /api/shout/stop`；
- 页面 `visibilitychange`/`pagehide` 时自动 stop，防止占着声卡。

### 6.3 后端会话与看门狗
- 全局 `SHOUT = {"sock":None,"ev":None,"ts":0,"bytes":0,"active":False}`（与现有 `SAY` 并列但独立会话，因 sayd 端是全局单例 PLAYER，**任一播放开始都必须先停另一个**）；
- 看门狗线程：超过 **3 s** 无新 PCM 片、或客户端断开、或单次超 **60 s** → 自动 `F_STOP` + 释放（与 sayd 自身 `IDLE_CLOSE=1.2s` 双重保险）；
- 发送节流：后端按到达速率即可（前端已按 100 ms 节拍发送），必要时加 200 ms 抖动缓冲再匀速推 sayd（缓解 Wi-Fi 抖动导致的忽快忽慢）；
- 断线自愈：借鉴 `say_wav()` 的 `_connect()` 重连逻辑（最多 6 次 × 2 s），但实时对讲重连会断音，优先保证看门狗及时停止并提示用户重按。

### 6.4 延迟预算
```
手机采集 + 100ms 分片       ~100 ms
HTTPS/Wi-Fi 上行            10~30 ms
后端转发 + 抖动缓冲         ~200 ms（可关缓冲降到 ~50ms）
sayd + ALSA(200ms buf)      60~150 ms
-----------------------------------------
合计                         ~370~480 ms（开缓冲）
                             ~220~330 ms（关缓冲，对讲级）
```
默认关抖动缓冲求低延迟；若现场出现忽快忽慢再开 200 ms 缓冲。

## 7. 互斥、安全与状态

1. **声卡独占**：sayd 的 `plughw:0,0` 是独占设备。所有入口——`/api/shout/clip`、`/api/shout/start`、`/api/audio/play`、`/api/audio/say`——开始前统一 `say_stop()` + `BRIDGE.audio_stop(0)`；反向也需在 `/api/audio/stop`、`/api/audio/play` 里加 `shout_stop()`，避免喊话与播报叠音或报 `Device or resource busy`。
2. **僵尸进程清理**：开流前按调研经验 `pkill -f "aplay -q -D plughw"`（经 103/205 免密通道）清理遗留占用，失败重试 1 次。
3. **啸叫**：手机靠近狗时回声，`echoCancellation:true` + 建议戴耳机；增益默认适中。
4. **鉴权**：新增 `/api/shout/*` 纳入现有 `_auth_ok()` 保护（当前 `AUTH_TOKEN` 为空即放行；若将来恢复口令，HTTPS + Cookie 机制自动生效）。
5. **流量统计**：`_meter_request()` 已在 `do_POST` 入口统一计入上行，喊话音频上传会自动反映到 `net.bps`，无需额外处理。
6. **状态回读**：`/api/status` 增加 `shout` 字段（`{active, mode, seconds}`），供前端与其他模块状态统一展示。

## 9. 部署与配置步骤

1. **证书**：204 上生成 `certs/cert.pem` + `key.pem`（§4），权限 600。
2. **TLS 服务**：新增 `s10yk-backend-tls.service`（或在现有 unit 加 drop-in 指定 `S10YK_PORT=18443` + `S10YK_TLS_CERT/KEY`），`daemon-reload && enable --now`。
   - 取舍：若选择"单实例双监听"以共享 `SAY`/`SHOUT`/`ARMED` 全局状态，需改 `main()` 起两个 `ThreadingHTTPServer` 线程（推荐，避免明文 18090 与 HTTPS 18443 的状态割裂——例如 HTTPS 端开始喊话后，明文端 `/api/status` 也应看到 `shout.active`）。
3. **sayd 无需改动**：确认 205 上 `s10yk-say` active、端口 18081 可达即可。
4. **前端**：`index.html` + `shout-processor.js` 上传 204 `/opt/s10yk/frontend/`（明文与 HTTPS 共用同一份文件）。
5. **防火墙/端口**：204 放行 18443（内网）；无公网映射需求则保持仅内网。
6. **回滚**：停用 TLS service 即回到纯 HTTP 现状，不影响运动/摄像头/语音播报。

## 11. 风险与限制

| 风险 | 影响 | 对策 |
|---|---|---|
| iOS / 微信内置浏览器不支持自签麦克风 | 无法使用 | 本次明确只支持 Chrome；阶段一提供"桌面录 WAV 上传"兜底 |
| 声卡被厂商节点/遗留 aplay 占用 | 喊话无声 / busy | 开流前互斥 + pkill + 失败重试；sayd 单实例保证不留残留 |
| 回声啸叫 | 刺耳 | echoCancellation + 建议耳机；不将手机贴近狗 |
| Wi-Fi 抖动（阶段二） | 卡顿/断续 | 100 ms 分片 + 可选 200 ms 缓冲；连续丢片触发看门狗停止重来 |
| 自签证书被 Chrome 拦截 | 麦克风不可用 | SAN 必须含实际访问地址；用户点"高级→继续"一次性信任 |
| 官方高声压（110 dBA）与双向对讲 | 本次做不到 | 属外挂"二代多合一"载荷 + 私有协议范畴；如项目需要另配硬件并索取协议文档 |
| 双实例状态割裂 | HTTPS 与 HTTP 状态不一致 | 采用 §9 推荐的单实例双监听方案 |

## 12. 代码改动清单与工作量

| 文件 | 改动 | 估算 |
|---|---|---|
| `backend/app.py` | HTTPS/TLS 启动与双监听；`/api/shout/{clip,start,pcm,stop,state}` 5 个接口；二进制 body 分支；`SHOUT` 会话 + 看门狗；`/api/status.shout`；各 audio 入口互斥补 `shout_stop()` | ~200 行 |
| `frontend/index.html` | 喊话 UI + `getUserMedia`/AudioWorklet 采集 + 两种发送模式 + 状态同步 | ~150 行 |
| `frontend/shout-processor.js` | AudioWorklet 处理器（Float32→Int16） | ~40 行（新增文件） |
| 服务单元 | `s10yk-backend-tls.service` 或 drop-in + 证书目录 | 配置 |
| sayd / 协议 | **不改** | 0 |

**里程碑**：① HTTPS + 麦克风授权打通（前置）→ ② 阶段一录完即播上线验收 → ③ 阶段二实时对讲上线验收。每步独立可回滚。

> 备注：本方案为设计输出，尚未编码实施。确认后可进入开发，开发完成需按 §10 逐项验收；阶段二建议在实际 Wi-Fi 环境测延迟与抖动后再定是否默认开启 200 ms 缓冲。

**实时对讲实现要点（与 §6 原设计的差异）**

1. **前端改为串行发送 + 自适应合批**：原设计"每 100ms 直接 POST"在并发下会乱序（多线程同时写 sayd socket → 帧字节交错 → 碎音）。现改为同一时刻只允许一个请求在飞、单请求最多合并 4 片，靠合批而非并发吃满带宽。
2. **不采用 chunked 流式上传**：仍走会话式 `start/pcm/stop`（规避 `BaseHTTPRequestHandler` 解析 chunked 的麻烦），但必须开启 **HTTP/1.1 keep-alive**，否则每秒 10 次 TCP+TLS 握手会直接吃掉实时性。
3. **队列上限与丢帧**：15 片（1.5s）封顶，超出丢最旧并计数——实时场景宁可掉字也不能让延迟无限累积。
4. **会话自愈**：`/pcm` 409 时自动重建会话一次；`SHOUT_GEN` 代次保护避免"松手收尾"误停新会话。
5. **缓冲位置**：延迟主要由 sayd 端 `aplay` 缓冲决定，实测链路（客户端 100ms 切片 + 网络 + 管道）仅 100~200ms。**已按 OPS-64 把 aplay 缓冲从默认 500ms 收到 250ms**（`-B 250000 -F 50000`，环境变量 `SAYD_BUFFER_US/SAYD_PERIOD_US` 可调），ALSA 实测协商 `buffer_size 4000 / period_size 800 frames @16k`。留 2.5 片（250ms）抗抖余量；若现场抖动导致断续，回调 `SAYD_BUFFER_US=400000` 重启 sayd 即可。
