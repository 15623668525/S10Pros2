# 控制台运动控制「前后左右、转向无效果」定位报告

| 项 | 内容 |
|---|---|
| 时间 | 2026-11-16 20:21–21:10（GMT+8） |
| 对象 | 106 主控板 / 服务器后端 / 205 zenoh 桥 |
| **结论** | **`/NAV_CMD` 通道对机器人完全无效（实测 `vel_x` 恒为 0）。根因是「NAV_CMD 仅在导航模式下生效」，而切换模式只能走 ASDU（TCP/UDP）协议，S10ykApp 后端从未实现该客户端** |
| 影响 | 速度控制这条功能从上线起就没有真正驱动过机器人（D-005「待实测」的欠账，本次实测结论为不生效） |

---

## 1. 实测：NAV_CMD 下发后机器人完全无响应

判据用 `MOTION_INFO.vel_x`（机器人**自报实际速度**），不依赖 UWB/ODOM（见 §4 为何不能用）。

| 场景 | 姿态 | 指令 | 实测 `vel_x` |
|---|---|---|---|
| A | 趴下 h=0.171 state=0 **gait=0** | x=0.05，10 Hz 持续 2 s（108 帧） | **0.0000** |
| B | 站立 h=0.387 state=17 **gait=4097（0x1001 常规）** | x=0.05，10 Hz 持续 2 s（121 帧） | **0.0000** |
| C | 站立 h=0.387 state=17 gait=4097 | x=0.15（限幅 0.09 m/s）持续 1.5 s | **0.0000** |
| D | 站立 h=0.390 state=17 **gait=12290（0x3002 导航模式步态）** | x=0.05，10 Hz 持续 **5 s**（49 帧） | **0.0000** |

**四种组合全部零响应。** 包括文档要求的"10 Hz 持续下发"和"导航模式步态"。

### 1.1 链路本身是好的（排除传输问题）

| 环节 | 方法 | 结果 |
|---|---|---|
| 后端 → zenoh → 205 → 106 | 后端连发 10 帧，106 逐帧落盘 | **收到 10 帧，10 Hz，严格 1:1** |
| `/MOTION_STATE` 下行 | 后端发 4（趴下）、1（站立） | **都生效**：狗真的趴下 / 站起（0.080→0.386） |
| 上行 `/MOTION_INFO` | `/api/status` | height/state/gait 实时刷新 |

→ **不是"指令到不了"，是"到了机器人不执行"。** 同一时间、同一通道，`MOTION_STATE` 好使，`NAV_CMD` 不好使。

---

## 2. 根因：NAV_CMD 需要「导航模式」，而模式只能走 ASDU 切

《S10 软件开发指南》2.3.1 原文：

> 【注意】该速度话题**仅在导航模式下生效**，且建议以 10Hz 的固定频率下发该话题。

而「使用模式」是另一个维度（1.2.2 使用模式切换）：

| 模式 | 值 |
|---|---|
| 常规模式 | 0 |
| **导航模式** | **1** |
| 辅助模式 | 2 |

> 常规模式下支持执行轴指令；导航模式下支持执行导航任务。

**关键点：模式切换不是 DDS 话题，而是 ASDU 请求**（Type `0x0010 0002` / Command `0x0050 0002`），走机器人对外的 TCP/UDP 接口：

| 接口 | 地址 |
|---|---|
| TLS（TCP + 加密） | `10.21.33.103:30003` |
| DTLS（UDP + 加密） | `10.21.33.103:30004` |

> 默认启用加密，关闭需厂商技术支持修改 `robotserve` 配置。

**而 S10ykApp 后端从头到尾没有 ASDU 客户端**（全文只有 sayd 音频那个 socket），速度控制只有 `/NAV_CMD` 一条路——所以永远进不了导航模式，NAV_CMD 永远不生效。

补充：步态切到 `0x3002` 理论上"会联动切到对应运动模式"（文档 2.2.x），但实测切过去（gait 回读 12290、height 0.390）后 NAV_CMD 仍无效，说明**固件并没有因为步态切换就真正使能导航模式下的速度接受**，或者还需要配套的"真实轴指令"使能。

---

## 3. 修复方案（两选一）

### 方案 B（推荐）：直接用 ASDU 的「真实轴控制」

厂商 App / 遥控器走的就是这条路，不依赖导航模式的前提链：

- Type `0x0010 0001` / Command `0x0011 0002`（真实轴控制），**仅导航模式下生效**，数据原样下发给执行端、不做额外限速。
- 常规模式则用 Type `0x0010 0001` / Command `0x0010 0002`（运动控制·轴指令，**仅常规模式和辅助模式下可执行**）。
- APDU = 16 字节协议头（同步字符 `0xeb` 等）+ JSON/XML 形式的 ASDU。

优点：一条链路直达，不依赖 NAV_CMD 是否被固件接受；缺点：需要实现 TLS 客户端（证书），或请厂商关闭加密。

### 方案 A：ASDU 切 Mode=1 + 继续用 NAV_CMD

先 TLS 连 `30003` 发「使用模式切换 Mode=1」，再按 10 Hz 发 NAV_CMD。链路更长，但改动集中在"切模式"这一步。

### 共同前提

两种方案都需要先实现 ASDU 客户端（16 字节头 + JSON ASDU + TLS）。这是本项目**尚未有任何代码**的部分，建议单独作为一项工作排期。

## 4. ⚠️ 本次调试中的两次误判（已更正）

调试中我一度用 UWB / ODOM 的位移判断"狗动了/自走了 2 米"，并用 `gait=0` 解释"控制无效"。**这两个结论都不成立**，原因是测量手段不可靠：

| 测量源 | 问题 |
|---|---|
| `/ODOM` | 站立/趴下时会跳变 0.3–0.45 m；历史 `Odom is out of range` 达 9 万次 |
| `/LIO_ODOM` | **无数据**（激光定位从未初始化） |
| UWB `/ubeacon_driver/location_result` | x 轴噪声 ±0.01 m 尚可，但 **y 轴 4 秒可漂 1.2 m**；且存在整段跳变（本次 x 从 82.05 变到 80.09，约 2 m） |

你在现场确认"没动过、一直原地"，与 `vel_x` 恒为 0 一致——**狗确实从未移动**，那些位移读数全是测量噪声/跳变。

**唯一可靠的判据是 `MOTION_INFO.vel_x`（机器人自报实际速度）**，后续调试请一律以它为准。
