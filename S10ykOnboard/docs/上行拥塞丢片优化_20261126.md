# 对讲上行拥塞丢片优化（2026-11-26，v3.5.8）

## 一、现象

- 下行轮询改造（v3.5.7）后对讲可正常进行，但状态栏显示 **"上行丢 69 片"**，用户感知为上行不稳定（狗端听到的说话声断续）。

## 二、定位（后端日志定量）

上行链路：手机麦 → AudioWorklet 每 100ms 产一片（3200B）→ `SHOUT_QUEUE` → `shoutPump()` 串行 POST `/api/shout/pcm`（每批最多 4 片）→ sayd 播放。

后端日志中每 50 片打点，`#51→#101` 间隔 6~9 秒，即接收节奏 **5.5~8.3 片/秒，低于生产速率 10 片/秒**：

```
15:35:32 → 15:35:38  50片/6s  ≈ 8.3片/s
15:36:30 → 15:36:39  50片/9s  ≈ 5.5片/s
```

后端每批到达即打日志（处理不慢），瓶颈在**公网链路每次 POST 的往返开销**：
每批最多 4 片（400ms 语音）× 一趟 RTT 开销 ~300ms → 泵稳态吞吐 ≈ 8 片/s，低于实时；队列（上限 15 片=1.5s）迟早打满 → 设计为"丢最旧保实时" → `SHOUT_DROP` 累积。20 秒丢 69 片 ≈ 6.9 秒语音被挤掉。

丢片只统计队列溢出；发送失败丢失的批次不计入（隐藏丢失）。

## 三、优化（仅前端 `frontend/index.html`，三处参数）

| 参数 | 旧 | 新 | 作用 |
|---|---:|---:|---|
| `SHOUT_BATCH` | 4（400ms/批） | **8（800ms/批）** | 积压时每请求携带量翻倍：一趟 RTT 追回的语音量翻倍，泵峰值吞吐 ≈10 → 27 片/s，才能追平实时速率。不增加固有延迟（数据本就在队列里，批大只是发送节奏合并） |
| `SHOUT_QMAX` | 15（1.5s） | **24（2.4s）** | 多扛 ~0.9s 网络抖动；配合丢最旧策略，短抖动不再掉字 |
| 发送重试 | 2 次、失败即弃批 | **3 次 + 120ms 退避** | 抖动时段不再连续撞墙；重试耗尽才提示"上行中断" |

"丢最旧保实时"的设计不变——宁可短暂落后也不越说越慢。

## 五、备注

- 公网 RTT 是硬约束：若 ISP 上行带宽/丢包更差，剩余手段只有压缩（如 opus）或降低采样率，当前未启用。
- 观察到部分时段上行 rms 低至 −77dBFS（静音片照发），白白占用约一半上行带宽；因 sayd 依赖持续流、门限跳发有断播风险，本轮未动，留作后续可选优化。
