# 实现方式审计：ROS2 话题 vs 直接抢占硬件

> 审计日期：2026-11-14　｜　代码基线：v2.3（`backend/app.py` 706 行 / `frontend/index.html` 410 行）
> 背景：机器人为共用硬件环境（厂商节点 + 我们的应用共存），应优先走话题避免资源抢占

---

## 一、结论摘要

> **v2.4 更新（2026-11-14 16:40）**：本轮已把"直接抢占硬件"的项按话题优先原则整改完毕，
> 并补齐了此前凭猜测的结论——详见 **第八节「整改结果」**。核心结论修正如下：

- **11 项功能走 ROS2 话题**（运动 4、状态 3、音频 4），符合"优先话题"原则。
- **自定义语音无法话题化**（硬约束，已用三重证据定性）：`/AUDIO/COMMAND` 只接受 `audio_id`，
  没有"播放任意文件"的 op；`audio.yaml` 不热加载；节点在第三个隔离容器内、资产为其私有副本。
- 因此整改目标从"改成话题"调整为 **"零占用 + 可让路"**：
  自定义语音改由 103 常驻播放器 `sayd` 代理（按需开设备、播完即 close、单实例、不留残留），
  **停止后 0.8 s 内声卡必释放、无 aplay 残留**（实测）。
- **音量无任何话题可用**（`/AUDIO/CONFIG` 只支持音色），保留 `amixer`；
  它只写混音器控件、不打开 PCM 流，**不属于抢占硬件**。
- 新发现并修复一个 P0 隐患：厂商调度器会被"无限循环 + `preempt=WAIT`"的项**静默卡死**，
  此后所有播报（含厂商自身提示音）全部无声且无法自愈。v2.4 改为"先 STOP 再 FORCE 下发"，
  1 次 STOP 即可解锁（实测）。

## 三、关键事实与证据

### 3.1 厂商音频节点是独立的 bare-DDS 进程

- `/AUDIO/STATUS` 的发布者节点名为 `_CREATED_BY_BARE_DDS_APP_`（非 rclpy/我们自己），订阅者 2 个（厂商 + `s10yk_bridge`）。
- **该进程不在 106（含 root）也不在 103 的用户态进程列表中**（`ps -eo pid,user,args | grep audio_node` 均为空），二进制却只存在于 106 的 `/opt/robot/share/robot_drivers/bin/audio_node`。
- 含义：我们**无法直接改它的资产表或重启它**（不知道宿主、也没有对应板的 root），因此"注册自定义音效走话题"这条路当前不具备条件。

### 3.2 声卡是独占资源（实测）

```
# 遗留 aplay 占住设备时的表现
$ play 1s PCM  → aplay: audio open error: Device or resource busy
$ cat /proc/asound/card0/pcm0p/sub0/status
state: RUNNING   owner_pid: 1337   （我自己遗留的 aplay -q -D plughw:0,0 -）
```
- 同一时刻任何其他程序（包括厂商音效）都无法打开该设备；
- 我们的 `say_wav()` 与系统音（话题）**共用同一个物理声卡**，因此理论上存在"我们占着 → 厂商提示音（请注意避让/充电中）播不出来"的风险。

### 3.3 麦克风不可用（实测）

| 尝试 | 结果 |
|---|---|
| `arecord -D plughw:1,0`（6ch 阵列） | `Device or resource busy`；`arecord -l` 显示 `Subdevices: 0/1`，`/proc/asound/card1/pcm0c/sub0/status` 为 `PREPARED, owner_pid=0` |
| 停掉 PipeWire（`pkill -x pipewire/wireplumber/pipewire-pulse`）后重试 | **仍 busy**，说明另有占用者（或崩溃残留句柄） |
| `arecord -D default` | 走 "ALSA ↔ PulseAudio PCM I/O Plugin"，录到 2s **纯静音**（RMS=0, peak=0） |
| 话题录音 `/AUDIO/RECORD_CMD` | `audio_ctl record start 2` → `Aborted`，状态话题无发布者 |

> 注：`owner_pid=0` + `PREPARED` 通常意味着"某进程打开后异常退出，句柄未释放"。可能与我们触发 `audio_ctl record start` 时厂商节点崩溃有关。

## 五、建议整改（按优先级）

### 5.1 自定义语音：先做"零抢占"，再谈"话题化"

**短期（可立即做）**
1. 开播前清理遗留：`pkill -9 -f "aplay -q -D plughw"`（避免 busy 连锁失败）；
2. 播放结束/异常后**立即释放**设备（进程退出即释放，但要防僵尸：给 aplay 加 `timeout` 或父进程 watchdog）；
3. busy 时自动退避重试（300ms×3），失败再报错；
4. 播自定义语音前先发 `/AUDIO/COMMAND STOP`，让厂商节点主动释放调度权（已有）。

**中期（需条件）**
- 把 wav 注册进 `audio.yaml` 增加 id（如 200+），改用 `/AUDIO/COMMAND` 播放，彻底不碰硬件；
- 前置：确认音频节点宿主 + 拿到该板写权限 + 明确重启方式；**当前均不具备，暂缓**。

### 5.2 音量

保留 `amixer`（无话题可用，且不占用 PCM）。可把守卫周期从 10s 放宽到 30s，减少 SSH 频次。

### 5.3 麦克风（喊话的 SPK 方向）

按以下顺序排查：
1. 确认 `card1` 的占用者（需 103 的 root 或 `fuser -v /dev/snd/*`）；
2. 尝试重新插拔 USB 音频模块 / 复位该 USB 设备（`usbreset`，需 root）；
3. 若确认是厂商节点崩溃残留 → 需重启该节点（先定位宿主）；
4. 恢复后才能评估"狗→手机"方向；在此之前，**双向对讲只能做单向（手机→狗）**。

## 七、附：本次审计顺带发现的实现细节

- `/AUDIO/COMMAND` 报文：`[op, audio_id, interval_ms, repeat(0=无限), priority, preempt]`；
- `/AUDIO/CONFIG` 报文：`[config_type(0=SET_VOICE,1=Voice,2=Voiceplay), value]`；
- `/AUDIO/STATUS` 的 `error_code` 实为"当前播放的 audio_id"，`state` 播放期间恒为 0（IDLE）——所以我们的"按时长回收框选"是必要设计；
- `audio_ctl` 是厂商提供的 CLI（`play/stop/record/voice/status`），可在 106 直接调用，等价于话题操作。

## 八、整改结果（v2.4，2026-11-14 16:40 实机验证）

### 8.1 先确认了三件此前只靠推测的事实

| # | 事实 | 证据 |
|---|---|---|
| 1 | **话题播放确实使用 103 的 `card0`**（共用硬件成立） | 下发 `/AUDIO/COMMAND` id=5 循环播放期间，103 `cat /proc/asound/card0/pcm0p/sub0/status` 连续为 RUNNING、`appl_ptr` 每 0.7 s 推进（8000→20000） |
| 2 | **我方占住设备时，厂商播报 20 ms 内即放弃**（没有重试排队） | 用 `dd` 灌 `plughw:0,0` 占住设备后下发 id=5：`/AUDIO/STATUS` 事件为 `(t=1.50, state=1, id=5)` → `(t=1.52, state=0)`，即 BUSY 仅 20 ms 就回落 IDLE，声音丢失 |
| 3 | **厂商调度器会被"无限循环 + `preempt=WAIT`"静默卡死** | 下发 `[0,6,0,0,9,0]`（repeat=0 无限、preempt=WAIT）后，再下发任何 PLAY 均无反应：`/AUDIO/STATUS` 完全不翻转、`/AUDIO/CONFIG_STATUS` 也无回应；用 STOP + FORCE 后立即恢复 |

### 8.2 为什么"自定义语音"不能改成话题（三重硬约束）

1. **报文定义**：`audio_dds_interface.hpp` 中 `/AUDIO/COMMAND` 只有 `op/id/interval/repeat/priority/preempt` 六个字段，`op` 仅 `0=PLAY(按 id) / 1=STOP`，**没有携带文件路径或 PCM 的通道**。
2. **不热加载**：`audio.yaml` 在节点启动时一次性读入（头文件里无 watcher/reload 逻辑），新增 id 需重启节点；此前 id=200 实测无声。
3. **资产不可达**：节点运行在第三个隔离容器内，`ps`/`/proc`/`fuser` 均不可见；其 `audio.yaml` 与 wav 是该容器的私有副本（挪走 NOS 上同名 wav 后播 id=4 仍正常），外部改动无效。

> 结论：在厂商开放"能播放任意文件"的话题（或允许热加载）之前，**自定义语音不可能 100% 话题化**。这是接口能力问题，不是实现选择问题。

### 8.3 实际做的改造（把"抢占"降为"零残留 + 可让路"）

| 项 | 改造前 | 改造后 |
|---|---|---|
| 播放器 | 每次 `ssh 103 aplay`（600 ms 建链；异常时进程长期占死设备） | 103 常驻 `sayd`（systemd `s10yk-say`，`Restart=always`），TCP 18081 推流，单实例 |
| 设备生命周期 | 跟随 ssh 子进程，可能残留 | `START` 才 open，`STOP`/断链**立即** close |
| 停止 | `kill` 本机 ssh 进程（跨机、可能杀不干净） | 发 `F_STOP` 帧 + 断链；控制连接已断时补发"孤儿 STOP" |
| 推流节流 | 一次性灌满（停止指令要等缓冲播完） | 按 `byte_rate` 实时节流 + `SO_SNDBUF=8192`，停止 ≤100 ms 生效 |
| 预置音效下发 | 直接 PLAY（`preempt=WAIT`，可能被卡死项吞掉） | `play_preset()`：先 STOP → FORCE 下发 → 500 ms 内无状态翻转则 STOP 重试一次 |
| 音量巡检 | 20 s | 60 s |

### 8.4 验证记录

| 项 | 结果 |
|---|---|
| 自定义语音播放 | `{"ok":true,"mode":"sayd","duration_ms":5880}`；103 `card0` RUNNING（`owner_pid=25196`）✅ |
| 停止即释放 | `say_stopped:true`；0.8 s 后 `card0: closed`、`pgrep -c aplay = 0` ✅ |
| 循环播报 | 连播 3 s 仍是同一 `owner_pid`（25372），无断音、无重建链 ✅ |
| 循环→停止 | 0.8 s 内 `card0: closed` ✅ |
| 卡死自愈 | 人为注入 `repeat=0 + WAIT` 卡死后，`/api/audio/play` 仍返回 `confirm:true`（首轮 STOP 即解锁，未触发重试）✅ |
| 预置音效 | `{"mode":"dds","confirm":true,"duration_ms":1217}` ✅ |

### 8.5 剩余约束（需厂商或硬件侧配合）

1. **循环喊话期间仍会丢厂商提示音**：喇叭只有一个播放子设备，且厂商播报 20 ms 内即放弃、不排队。软件侧只能做到"停止后立刻还给厂商"。
   可选折中：`SAY_LOOP_GAP=1.4`（环境变量）让每轮之间**真正释放设备约 1.4 s**，给提示音留插入窗口，代价是喊话有明显停顿。
2. **麦克风（喊话"狗→手机"方向）仍不可用**：`hw:1,0` 长期 busy、`default` 走 PulseAudio 只得静音，需现场排查 USB 音频模块。

## 九、视频通道核查（2026-11-14 17:00，v2.4 期间补测）

### 9.1 结论

- **现成可用的图像话题只有 1 个**：`/DEPTH_IMAGE`（`sensor_msgs/Image`，RELIABLE，2 个 bare-DDS 发布者）。**当前无数据**（连续监听 12 s 零消息），推测深度相机仅在特定状态（导航/RL）开启。
- **彩色视频不是"只能 RTSP"，而是厂商把 DDS 输出关掉了**：4 路 USB 相机每路都配了三种输出 sink —— `dds` / `rtsp` / `rtcx`，配置中 `dds.enabled=false`、`rtsp.enabled=true`、`rtcx.enabled=true`。
- 因此当前实际可用的彩色视频通路 **只有 RTSP**（本机 `8554`）与厂商云 P2P（RTCX）。

### 9.2 相机与输出配置（`/var/opt/robot/conf/usb_cam_multi_node/multi_camera_params.yaml`）

| 相机 | 设备 | 采集 | RTSP 路径 | DDS 输出 | 云端 |
|---|---|---|---|---|---|
| camera1 尾部 | `/dev/usb_cam_tail0` | 1280×720 | `rtsp://<host>:8554/video0` | `enabled:false` | rtcx 2048kbps |
| camera2 左侧 | `/dev/usb_cam_left0` | 1280×720 | `.../video2` | `enabled:false` | rtcx 2048kbps |
| camera3 头部 | `/dev/usb_cam_head0` | 1280×720 | `.../video4` | `enabled:false` | rtcx 2048kbps |
| camera4 右侧 | `/dev/usb_cam_right0` | 1280×720 | `.../video6` | `enabled:false` | rtcx 2048kbps |

- RTSP 输出经 MPP 硬编 H.264，裁剪 **1024×576**、`framerate: 30`、单路 2048 kbps，`queue_duration_ms: 300`。
- DDS sink 的参数只有 `publish_format: auto(优先mjpeg)/nv12/mjpeg/none`，**没有 topic 字段**（话题名应为节点内置），需开启后实测确认。
- 实测（`ffprobe`，四路一致）：`codec=h264, 1024x576, 30/1`，**SDP 只有一条 video track，无音频**。

### 9.3 RTSP 可用性实测

| 项 | 结果 |
|---|---|
| 端口 | 103 `:8554`（mediamtx，`paths: video0/video2/video4/video6`，`source: publisher`） |
| DESCRIBE | 四路均 `200 OK`，`m=video 0 RTP/AVP 96` + `a=rtpmap:96 H264/90000` |
| 配置位置 | 运行时 `/var/opt/robot/conf/usb_cam_multi_node/mediamtx.yml`（`/opt/robot/share/...` 下是副本） |
| API | 配置里 `apiAddress: :9997`，但 103 实际**未监听 9997**，无法用 HTTP API 管理 |

### 9.4 打开 DDS 图像输出的代价

1. 改 `multi_camera_params.yaml`：对应相机 `outputs[dds].enabled: true`（建议 `publish_format: mjpeg`）。
2. **必须重启 `media_master.service`**（相机节点）。该服务在厂商容器内：106 的 `systemd` 看不到该 unit，进程表也看不到（drsec 沙箱）；只能通过 nodectl 的 `/NODECTL_CMD` 话题请求重启，或整机重启。
3. 副作用：重启期间 4 路 RTSP 与云端 RTCX 推流全部中断；若开 NV12，720p×30×4 ≈ 166 MB/s 走 DDS，订阅端解包/解码开销大；开 MJPEG 亦为逐帧 JPEG，CPU 与带宽（每路数 MB/s）都不低。

### 9.5 浏览器播放的可选方案（实测数据）

| 方案 | 做法 | 实测 |
|---|---|---|
| A. 后端转 MJPEG（推荐） | `ffmpeg -rtsp_transport tcp -i rtsp://.../video0 -vf fps=8,scale=640:-2 -q:v 5 -f mjpeg -` 以 `multipart/x-mixed-replace` 输出，前端 `<img>` 直接显示 | 8 fps、640 宽、q=5：6 s 出 1.4 MB（≈0.24 MB/s），CPU `utime 2.56s / 4.73s` ≈ 单核 54% |
| B. 定时快照 | 每 1 s 抽一张 JPEG，前端轮询刷新 | 640 宽 q=6 每张 ≈30 KB，CPU ≈ 单核 31% |
| C. mediamtx 开 HLS/WebRTC | 需改 mediamtx 配置并重启该服务（厂商托管，同 9.4 风险） | 未验证 |

> 建议：预览用 A（唯一改动只在我们的后端），**不要**为了"走话题"去开 DDS 图像——除了风险，DDS 只在本机可用，浏览器还是要转码。

### 9.6 顺带发现（与"喊话"相关）

厂商相机配置里已存在**双向对讲实现**（`talk` 段）：
- `talk.send`：`source: shm`（`/dev/shm/media/shm_audio_sock`）或 `alsa plughw:1,0` → G711A → 云端；
- `talk.recv`：云端 → G711A 解码 → **播放到 `plughw:CARD=rockchipes8388,DEV=0`**（扬声器），`use_pulseaudio: false`。

即厂商自己就有"云端→扬声器"的播放通道，但需 RTCX 云账号（`product_key` / `device_name` / `device_secret`）与 P2P 会话。这为"喊话不占本地声卡"提供了第 4 条潜在路径。

## 十、SPK 不独占硬件的可行性专项（2026-11-14 20:30，v2.5 期间实测）

> 起因：v2.4 把"抢占"降级为"零残留 + 可让路"后，循环喊话仍会丢厂商提示音。问题是：**能不能像混音器那样，让两路音频同时出声、谁也不占死设备？**

### 10.1 结论先行

| 问题 | 答案 |
|---|---|
| 有没有**纯软件**且**无需厂商配合**的混音方案？ | **没有。** 三条可能路径全部实测堵死（E1/E3/E6） |
| 有没有可行的"不独占"方案？ | 有，但都要落在**物理层**或**厂商侧**：① 给我们的语音加一路独立播放设备（USB 声卡/小喇叭），与厂商物理隔离；② 厂商把播放设备名改成 `dmix`（本机 dmix **实测可用**，只差这一行） |
| dmix 到底能不能用在这块 codec 上？ | **能。** 同一块 card0 上两个客户端并发播放均成功，底层只有一个 `owner_pid`（E2）。这是本次最有价值的发现 |

### 10.2 六条假设逐条实测（证据链）

| 编号 | 假设方案 | 实测做法 | 结果 | 结论 |
|---|---|---|---|---|
| **E1** | 硬件多流混音（两进程直接开同一设备） | 进程 A 持 `plughw:0,0` 播放，进程 B 并发打开 | B: `audio open error: Device or resource busy`，rc=1；`/proc/asound/pcm` 显示 card0 **`playback 1`**，`aplay -l` 显示 **`Subdevices: 1/1`** | 单播放子流，**硬件层面必然独占**，与软件写法无关 |
| **E2** | dmix 软件混音是否可用 | 写 `pcm.dmixed`（`type dmix`，slave `hw:0,0` 48 kHz S16_LE），两个 `aplay -D dmixed` 并发 | 两个客户端**均 rc=0** 正常播放；`sub0/status` 只有 1 个 `owner_pid`（dmix 持有 hw，客户端在 dmix 内混合） | **dmix 在这块 codec 上完全可用** → 只要两个客户端都走 dmix，就能真混音 |
| **E3** | 厂商是否已经在走某个共享层 | ① dmix 持卡 12 s，期间下发 `/AUDIO/COMMAND` id=4；② 反向：厂商播放时我们用 dmix 打开 | ① 下发返回 `confirm:true`（仅代表 DDS 发出），但 `/AUDIO/STATUS` 全程 `state:0,id:0` —— **一声未出**；② dmix 报 `snd_pcm_dmix_open: unable to open slave` + `Device or resource busy` | 厂商**裸开 hw，完全绕过任何共享层**；双向互斥，dmix 对它无效 |
| **E4** | 改掉厂商的播放设备名（重定向到 dmix） | 读 `audio.yaml` 全文 + 查 103 上资产路径 | `play:` 段**只有 `enable` / `volume`，没有 `device` 字段** → 设备名写死在程序里；103 上 `/opt/robot` 只有 `bin`/`scripts`，`audio_node_assets` 不存在，`/userdata`（容器 overlay 宿主路径）在我们容器内不可见 | 配置改不了、资产摸不到，**必须厂商改** |
| **E5** | 把音频注入厂商自己的 media 服务（`/dev/shm/media/shm_audio_sock`） | `/proc/net/unix` 定位 inode、权限检查、读 `audio.yaml` 段归属 | socket 存在（unix stream，属主 `user`，**我们能连**），但它属于 `wakeup` 段：`input_device: "hw:1,0"`（6ch 麦克风阵列）+ `shm_socket_path` = 麦克风**上行旁路**（→ 云端） | 是**采集/上行**入口，不是播放入口，**不能用来放音** |
| **E6** | 虚拟声卡 + 用户态混音（经典 ALSA loopback 混音） | `modinfo snd-aloop` | `ERROR: Module snd-aloop not found` —— 该内核**未编译** loopback 模块 | 无 loopback 卡可建，此路不通（且需 root） |
| **E7** | 板载有没有第二路可播设备 | 枚举 `/proc/asound/*`、`amixer scontrols` | card1 = `NationalChip Uac Speaker`（USB，full speed），**只有 `pcm0c`（capture），无 playback**；ES8323 的 `Speaker` / `Headphone` 是**同一路 PCM** 的两个模拟开关（`Speaker: on`、`Headphone: off`），不是两条独立音频流 | 板载没有可用的第二路播放入口 |

> 权限边界补充：103 上 `user` 属于 `sudo` 组但 `sudo` 需密码（`sudo -n true` 被拒），`/opt/containerd`、`/run/containerd` Permission denied —— 即使有 ALSA 层方案，也缺 root 与容器内访问。

### 10.3 可落地方案对比

| 方案 | 做法 | 与厂商冲突 | 成本 | 结论 |
|---|---|---|---|---|
| **A. USB 小喇叭插 106（推荐）** | 106：8 条 USB 总线全空、`snd_usb_audio` 已内建（builtin）、`aplay`/`amixer` 在位、`/dev/snd` 已挂载（现有 `seq`/`timer` 节点）。语音从 106 本地输出，**完全不碰 103 的 card0** | 无 | 一个 USB 音箱 ¥20–60 | **首选**：零改厂商、零拆机、可回滚；代价是多一个物理喇叭 |
| B. USB 声卡插 103 + 独立小喇叭 | 103 的 UAC 支持已被 card1 证明；同样物理隔离 | 无 | 同上 | 备选，两个喇叭都在机器人身上 |
| **C. 厂商把播放设备改 dmix** | `play:` 增 `device: "dmixed"`（或把写死的 `plughw:` 改为走 `default`→dmix） | 无 | 厂商改一行 | **技术上最优**：E2 已证明 dmix 可用，改完就是真混音（两路同时出声、谁也不丢） |
| D. 音频 id 化 / 按路径播放 | `/AUDIO/COMMAND` 支持"注册音效"或"播任意 wav 路径" | 无 | 厂商开发排期 | 最优但依赖排期 |
| E. 云端 `talk.recv` | 复用厂商"云端→扬声器"通道，由厂商进程播放（见 9.6） | 无 | RTCX 云账号 | 可行，但依赖 P2P 会话、有网络延迟 |
| F. 模拟混音器 | 取 ES8323 耳机口（line 级，当前 off）+ USB 声卡输出，混入独立功放 | 无 | 混音板 + 拆机改线 | **不建议**：需切断本体喇叭线、喇叭级与 line 级电平不匹配，施工风险高于收益 |
| G. 现状时间片让路（v2.4） | 播完立即 close、空闲 1.2 s 释放、`SAY_LOOP_GAP` 让窗 | 仍会丢提示音 | 0 | 已上线，作兜底 |

### 10.4 给厂商的最小需求（按性价比排序）

1. **`audio.yaml` 的 `play:` 增加一个 `device` 字段**（默认值保持现有 `plughw:CARD=rockchipes8388,DEV=0`），我们自己配成 dmix 名。改动量≈一行配置，收益是彻底消除抢音。
2. `/AUDIO/COMMAND` 增加"按文件路径播放"或"注册音效 id"，即可完全取代本地播放。
3. 若上游短期不改：接受方案 A（物理第二路），我们侧改动最小、可随时回滚。

### 10.5 若选方案 A 的现场动作清单

1. USB 小喇叭插 106 任一空口。
2. 确认 `ls /dev/snd` 出现 `pcmC0D0p`、`aplay -l` 列出新 card（**容器内热插拔能否生成设备节点需现场验证一次**，当前 `/dev/snd` 只有 `seq`/`timer`）。
3. 后端 `say_wav` 由"TCP 推给 103 的 sayd"改为"106 本地 `aplay`"（无需再为让路做 close/节流，逻辑反而更简单）；`s10yk-say` 可保留作回滚。
4. 厂商 card0 完全不动，`/AUDIO/COMMAND` 照旧使用。

### 10.6 复现命令

```bash

sleep 0.8; aplay -D plughw:0,0 -t raw -f dat -d 1 /dev/zero   # → Device or resource busy

aplay -D dmixed -t raw -f dat -d 1 /dev/zero                  # 客户端 2 → rc=0 即混音可用

```

## 十一、控制台接入前摄像头（低时延）方案调研与实现（2026-11-15，v2.6）

> 需求：控制台网页看机器狗**前摄像头**实时画面，时延尽量低；4 路机位可切换；不看时不要常年吃 CPU。

### 11.1 可选通道复核（承接第九节）

| 通道 | 现状 | 结论 |
|---|---|---|
| DDS `/DEPTH_IMAGE` | 无发布数据（9 节实测 12s 零消息） | 不可用 |
| DDS 彩色图像口 | 默认 `enabled:false`，开启需重启厂商 `media_master.service`（四路 RTSP + 云端推流全断），且 DDS 只有本机订阅者，浏览器仍需二次转码 | **排除** |
| 4 路 RTSP（103:8554，`video0/2/4/6`） | H.264 1024×576@30 2048kbps DESCRIBE 200 OK，LAN 内稳定 | **唯一现实入口** |

### 11.2 浏览器低时延方案对比

| 方案 | 链路 | 端到端时延（预估值） | CPU（106） | 改动量 | 备注 |
|---|---|---|---|---|---|
| **A. MJPEG multipart（v2.6 采用）** | ffmpeg 拉流→缩放/JPEG 编码→HTTP `multipart/x-mixed-replace`→前端 `<img>` | **约 0.3–0.6 s**（源编码 ≈100ms + 1/15fps≈67ms + 转码/网络/渲染） | 单路约占 0.5–1 核（960 宽 15fps） | 后端 1 个接口 + 前端 `<img>`，无新组件 | 兼容性最好；帧总线多端共享；带宽 ≈0.5–1 MB/s |
| B. H.264 透传 → WebSocket → MSE (fMP4) | ffmpeg `-c copy` 出 fMP4 分片→自写 WS 服务→MediaSource 解码 | 约 0.3–0.5 s（分片粒度决定下限） | ≈3–5%（不转码） | 自写 WS 服务 + MSE 播放器 ≈200 行 | CPU 最低；受源流 B 帧/GOP 影响，需 ffprobe 确认 `has_b_frames` |
| C. 自建 WebRTC（mediamtx WHEP） | ffmpeg `-c copy` 推本机 mediamtx→浏览器 WHEP | **约 0.15–0.3 s，最优** | ≈3–5% | 新增常驻服务 + WHEP JS；mediamtx 二进制需外网下载（106 无外网，可 PC 侧传） | 时延天花板；多一个组件要运维 |
| D. HLS / LL-HLS | ffmpeg→HLS 分片 | 2–8 s（LL-HLS 也要 ~2s） | 低 | 中 | 时延不达标，排除 |
| E. 定时快照轮询 | 每 1s 抓一张 | 1–2 s | 31% 单核 | 最小 | 只够"看个方向"，不满足低时延 |

选型逻辑：**先 A 后 C**。A 当天可落地、零新组件，0.3–0.6s 对遥控观察够用；若现场实测不达标（要求 <300ms），再上 C（代码与文档已留好演进路径，前端只需把 `<img>` 换成 WHEP 播放器）。

### 11.3 v2.6 实现（后端 `app.py`）

- `CamSource`（每机位一个）：懒启动单 ffmpeg 进程（拉流→`fps=15,scale=960:-2`→`-q:v 4` MJPEG 到 stdout），标记者线程按 JPEG marker（SOI/EOI/SOS 熵区扫描）切帧存 `frame/seq`，`Condition` 通知订阅者。
- **低时延输入参数**：`-fflags nobuffer -flags low_delay -avioflags direct -probesize 500000 -analyzeduration 2000000 -max_delay 0`——去掉 ffmpeg 启动探测与抖动缓冲（实测这组参数比默认少 1–2s 的首帧与稳态缓冲）。
- 多端共享：一个 ffmpeg 服务所有观看者（`/api/cam/probe` 可查各机位客户端数）；**无客户端 20s 后 reaper 线程自动停流**，不常年占 CPU。
- 接口：`GET /api/cam/stream?src=videoN`（multipart，首帧最长等 8s，取不到回 502）、`GET /api/cam/probe`。
- 前端：摄像头卡片（机头/下视/机尾/侧向 tab + 视频开关），开关与机位持久化到 localStorage，刷新自动恢复。

### 11.4 时延构成与现场实测方法

构成（预估）：源端编码 ≈100ms + RTSP/TCP 传输 ≈20ms + 解码 ≈35ms + fps 滤波平均 ≈33ms + JPEG 编码 ≈15ms + 网页渲染 ≈30ms ≈ **0.25–0.35s**，加上浏览器抖动按 **0.3–0.6s** 评估。

现场玻璃到玻璃实测方法（3 次取平均）：手机打开毫秒级计时器 → 正对前摄像头 → 同时看网页画面里的计时读数与手机真实时间 → 差值即时延。判定：≤500ms 合格；>800ms 触发方案 C 升级。
