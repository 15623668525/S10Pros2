## 5. z 坐标的语义：不是实测高度，是「基准面 + 先验」

**结论：z 不随实际抬升变化，它等于 map 基准面 3.0 m 加上参数 `expect_z` 的先验值，属于常数而非测量量。**

实测证据（受控实验，逐帧观察 z）：

| 操作 | 输出 z 变化 |
|---|---|
| 基线（`expect_z`=0.4 生效中） | 3.402 → 3.402 |
| **写入 `expect_z = 0.8`** | 3.636 → **3.802**（= 3.0 + 0.8）→ 回落到 3.609 |
| 写入 `expect_z = 0.4` | 3.475 → 3.408 → 缓慢回升 3.564 → 3.643 → 3.651 |
| 60 s 后自然收敛 | **3.600**（= 3.0 + ROM 里的 0.6） |

读数：

1. **z 确实跟随 `expect_z`**——写 0.8 时 z 立刻冲到 3.80，证明 z 由先验决定，而不是声学/无线电测得的高度。
2. **写入值只在 RAM 生效**——写 0.4 后 z 短暂降到 3.41，但几十秒内被设备 ROM 里的 0.6 拉回，最终稳定在 **3.600**。设备会周期性重载 flash 参数。
3. **根因是 19 个基站全部共面（map_z 恒 3.0）**，垂直方向没有几何约束，只能靠先验。对地面 2D 导航无影响，但**不能把 z 当真实离地高度使用**。
4. 当前 ROM 值 `expect_z = 0.6`，输出 z = 3.0 + 0.6 = **3.60**，自洽。

> 待确认：标签装在狗身上，实际离地高度是 0.6 m 吗？若是，现状即可；若量出来是 0.4 之类，需要写进 flash（用厂商上位机/`run_time_param_write` 持久化），否则重启后又回到 0.6。

## 6. 验证中发现的问题

### 6.1 【已澄清并已清理】双类型冲突是诊断动作自身引入的端点残留，不是既有故障

> 本条初版定性为"预先存在的空壳发布者"，**20:00 追查后已更正**：它是我 19:34 开始跑诊断脚本的副产物。

**现象**：

```
$ ros2 topic info /ubeacon_driver/location_result_pose
Type: ['geometry_msgs/msg/PoseStamped', 'geometry_msgs/msg/PoseWithCovarianceStamped']
Publisher count: 6          # 3 个 PoseStamped + 4 个 PoseWithCovarianceStamped
```

**四面证据指向同一条因果链**：

| 证据 | 内容 |
|---|---|
| ① 端点归属 | 所有 `_CREATED_BY_BARE_DDS_APP_` 端点的 GID 前缀都是 `0a.4f.34.4a.a3.9f.3d.e0.8e.35`，与它订阅 `location_result` 的端点**完全一致** → 同一个 DDS 参与者，即 205 的 zenoh 桥 |
| ② 时间戳 | 205 桥日志中 17:15–17:58 的 6 条 pose 路由**全是纯 `PoseStamped`**；第一条 `PoseWithCovarianceStamped` 出现在 **19:34:36**，正是我第一次运行 `collect_loc.py` 的时刻；19:41:08、19:43:41、19:43:59 各再来一次，与后续几次运行严格对齐 |
| ③ 排除外部源 | 服务器 zenoh 桥（`/opt/zenoh-dds/srv/zenoh-bridge-dds`）日志中该 key **0 条记录**；服务器上的 Nooploop 上位机 `tool_v1.3.0.86` 走的是 **MQTT 1883**（与网关 `<UWB_GW_ID>`、标签 `<UWB_TAG_ID>`、基站 <UWB_ANCHOR_ID> 通信）+ UDP 9740，**完全不碰 DDS** |
| ④ 反向验证 | 20:01:30 重启 205 桥后，106 上立刻恢复 `Type: geometry_msgs/msg/PoseStamped`、publisher=1，`location_result` 仍 23 Hz |

**完整因果链（4 步）**：

1. 驱动 `ubeacon_driver` 只发布 `PoseStamped`——这是唯一合法的类型。
2. 我的诊断脚本按 `PoseWithCovarianceStamped` 去订阅同名话题。ROS2 RMW **在类型一致性校验失败之前，就已经把"本话题要求该类型"的端点/类型声明送进了 DDS**，于是订阅创建报错，但 DDS 层留下了这个类型的声明痕迹。
3. 205 的 zenoh 桥是**全量桥接**——`/opt/zenoh/bridge-103.json5` 只有 4 行（`timestamping` + `scouting`），没有任何 `dds2zenoh`/`zenoh2dds` 白名单，默认 `**`。它看到本地 DDS 上该 topic 有该类型的 reader 侧声明，就按此类型创建 `Zenoh→DDS` 路由并写回 DDS。
4. 于是同名话题上出现第二种类型；且**每查询/订阅一次就多一个 writer**（实测 4 → 7 增长），因为桥认为"还有 reader 在等这个类型"。

**为什么这会让订阅方"创建失败"而不是"收不到数据"**：DDS 规范里 topic 的类型是**每话题唯一**的，rmw 在 `create_subscription()` 时会校验已存在 topic 的类型；两种类型并存时，用错类型的一方直接抛 `incompatible type` 错误，连接根本建不起来。

**已处理**：20:01:30 `systemctl restart zenoh-bridge-dds`（205），端点全部重建，双类型消失。

**真正该记的教训**：全量桥接会把 DDS 域里任何一次"类型误声明/端点抖动"放大成 zenoh 路由再回灌本地，形成持久化的污染。**根治办法是给 205 与服务器桥加话题白名单**，只桥接实际需要的那几条（`rt/NAV_CMD`、`rt/MotionState`、`rt/ODOM`、`rt/ubeacon_driver/*` 等），而不是 `**`。在那之前，下游一律用 `PoseStamped` 订阅。

### 6.2 `expect_z` 不落 flash，重启/重载即回滚

见 §5。写入 `param_write` 只改 RAM，设备会自动回到 ROM 值。**不要靠 ROS 参数“改死”这个值**，需要持久化请用厂商上位机。

### 6.3 6.2% 的帧只有 2 个基站

见 §3.2。建议下游加门限：`anchors >= 3` 才使用该帧，否则保持上一帧或降权。

### 6.4 标签电量读不到

`heartbeat.battery_percent = 0`、`battery_charging = false`，而 `hardware_enabled_uart/uwb = true`。说明标签走 USB 供电、未接电池检测电路，**无法远程监控电量**。若后续要脱离 USB 使用，需注意这一点。

### 6.5 y 向漂移 1.75 m

见 §2。属基站几何 + 滤波特性所致，非故障。若导航要求优于 0.5 m，需要在应用层做滤波（如滑动平均/EKF），或让标签更靠近某一排基站。

## 7. 可用性评估

| 场景 | 是否可用 | 说明 |

| 全局位姿初始化 / 粗定位 | ✅ **可用** | 23 Hz、零错误码、坐标落在基站包围网内，静态抖动 x±0.12 / y±0.39 m |

| 窄通道/贴边通过（要求 <0.3 m） | ⚠️ **需滤波** | y 向 1.75 m 游走需平滑后才能用 |

| 直接喂给现有导航栈 | ❌ **尚未接入** | 导航侧无任何消费者，需另做 TF/融合节点 |
