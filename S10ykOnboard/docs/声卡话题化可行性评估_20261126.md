# 声卡输入输出话题化可行性评估

> 评估日期：2026-11-26 13:20　｜　基线：v3.5　｜　依据：现场实测 + 《实现方式审计_话题与硬件》
> 问题：能否把当前声卡的输入（mic）/输出（spk）发布成 ROS2/DDS 话题，替代或补强现有 sayd/arecord 直驱方案？

---

## 一、结论摘要

| 问题 | 答案 |
|---|---|
| 205 本地能否 pub/sub 音频话题？ | **能**，rclpy + std_msgs 齐备，声卡可用，半天可出 PoC |
| 能否跨机（205 → 204）传音频话题？ | **未知，需 PoC**——现有 DDS 桥对话题不是全量透传（`MOTION_INFO` 过桥、`STEER` 不过桥） |
| 话题化能解决"厂商提示音丢失"吗？ | **不能**——card0 单 playback 子流，话题化不改变物理独占 |
| 对当前点对点对讲有收益吗？ | **有限**——点对点场景话题的一对多优势用不上 |
| 值得做吗？ | **看需求**：接 ASR/录音留存等多消费者 → 值得；只为规范对讲 → 不值得 |

**一句话**：本地技术无障碍，跨机是最大风险点，且话题化治不了真正的痛点（声卡独占）。

### 2.2 声卡硬件能力

| 设备 | 方向 | 实测状态 |
|---|---|---|
| card0 rockchip-es8388 | capture (pcm0c) + playback (pcm0p) | 各 1/1 subdevice；当前 `closed` |

### 2.3 麦克风实录验证

```
arecord -D plughw:1,0 -f S16_LE -r 16000 -c 1 -d 1 /tmp/mic_test.wav
→ 32044 B / 1 s，ch=1 rate=16000
→ RMS=1423 peak=4693（真实环境声，非静音）
```

**结论**：输入源可用。旧审计"麦克风不可用（RMS=0）"的结论已于 OPS-66/67 作废。

### 2.4 跨机通信链路

| 链路 | 现状 |
|---|---|
| 204 → 205 sayd 推流 | TCP 18081，**已验证可用**（当前 v3.5 对讲/喊话走这条） |
| 204 zenoh-bridge-dds | 在跑：`-l tcp/0.0.0.0:7447` |
| 204 订阅 `/MOTION_INFO` | ✅ 通过桥收到（3432 帧） |
| 204 订阅遥控器 `/STEER` | ❌ 收不到（同话题在 106 本地域能抓到） |

**风险点**：DDS 桥对话题**不是全量透传**。新定义的 `/audio/in`、`/audio/out` 能否过桥没有先例，必须 PoC 验证，不能想当然。

## 三、三种实现路径

### 路径 A：本地话题化（205 内部，不跨机）

```
205: arecord → rclpy 节点 pub /audio/in → 205 本地订阅者 → TCP/HTTP → 204 → 手机
```

- 消息：`std_msgs/ByteMultiArray`（16 kHz mono S16，10 ms 分片 = 320 B/帧，100 fps）
- 带宽：32 KB/s（256 kbps）
- 改动：205 新增采集节点 + 订阅转发节点
- **优点**：不依赖跨机桥，风险最低
- **缺点**：对讲链路多绕一层，话题优势（一对多）仍用不上

### 路径 B：跨机话题化（205 pub → 204 sub）

```
205: arecord → pub /audio/in ──[zenoh 桥]──▶ 204: sub → HTTP → 手机
204: pub /audio/out ──[桥]──▶ 205: sub → aplay card0
```

- **前置 PoC**：先用一个低频测试话题（如 `/audio/ping` 发递增整数）验证能否过桥，再上音频流
- QoS：音频用 best-effort + 小 history depth，避免可靠重传堆积延迟
- **风险**：跨机桥不通则整个方案作废；音频连续流对桥参数敏感
- **收益**：真正的发布/订阅解耦，后端不再需要直连 sayd

### 路径 C：只做输入话题化（推荐先做）

```
205: arecord → pub /audio/in → 本地订阅 → 现有对讲链路上行
```

- 只把 mic 采集侧话题化，播放侧继续 sayd
- 采集侧一对多：对讲 + 未来 ASR/录音留存可同时订阅
- 播放侧不动，不引入新的声卡竞争
- **最小风险，最大灵活性**

## 四、方案对比

| 维度 | 当前方案（v3.5 直驱） | 路径 A 本地话题 | 路径 B 跨机话题 | 路径 C 仅输入话题 |
|---|---|---|---|---|
| 上行链路 | arecord → SSH → 204 | arecord → /audio/in → 订阅 → 204 | arecord → /audio/in → 桥 → 204 | arecord → /audio/in → 订阅 → 204 |
| 下行链路 | 204 → TCP 18081 → sayd → aplay | 不变 | 204 → /audio/out → 桥 → 205 aplay | 不变 |
| 多方消费 | ❌ | ✅ 一对多 | ✅ 一对多 | ✅ 仅输入侧 |
| 跨机风险 | 无（TCP 已验证） | 无 | **高**（未验证） | 无 |
| 声卡独占 | 存在，靠 0.8s 释放 | 仍存在 | 仍存在 | 仍存在 |
| 改动量 | 已上线 | 中（2 节点） | 大（2 节点 + 桥配置） | 小（1 节点） |
| 延迟影响 | 基线 | +10~30 ms | +20~100 ms（估） | +10~30 ms |
| 适用场景 | 手机↔狗点对点 | 本地多消费者 | 完全解耦架构 | 未来接 ASR/留存 |

## 五、必须正视的两个约束

1. **话题化解决的是"数据分发"，不是"声卡独占"**
   card0 只有 1 个 playback 子流；厂商音频节点裸开 `hw:0,0` 绕过 dmix。话题化后播放订阅者仍要 open card0，冲突机制不变。审计 §10 已实测 E1~E7 全部堵死纯软件混音路径。
   - 当前特殊窗口：厂商 audio 节点假死（见当日工作日志），card0 全空，此刻无冲突。
   - 厂商修复后冲突回归，仍需物理第二路（USB 小喇叭）或厂商改 dmix。

2. **跨机桥不可想当然**
   `/MOTION_INFO` 能过、`/STEER` 不能过，说明桥有过滤或域隔离。音频话题必须先做 ping 验证。

## 六、推荐决策

| 你的真实需求 | 建议 |
|---|---|
| 只是想让对讲/喊话更规范 | **不做话题化**——维持 sayd，收益不抵复杂度 |
| 未来要接本地语音识别 / 录音留存 / 多路分析 | **做路径 C**（仅输入话题化），先落地再扩展 |
| 要彻底解耦前后端、后端不再直连业务板 | **做路径 B**，但先完成跨机 ping PoC |
| 要解决循环喊话丢失厂商提示音 | **话题化无效**——物理第二路 USB 小喇叭 或 厂商改 dmix |

### 最小 PoC 步骤（若决定做路径 C）

1. 205 写 rclpy 采集节点：`arecord` subprocess → `ByteMultiArray` pub `/audio/in`，10 ms 分片
2. 205 本地 `ros2 topic hz /audio/in` 验证 100 fps、带宽 32 KB/s
3. 本地订阅节点落 WAV，回放比对 RMS/peak 确认无失真
4. 如需跨机：先发低频 `/audio/ping` 验证 204 可见，再切音频流
5. 实测端到端延迟（采集 → 手机出声），与当前基线 0.3~0.5 s 对比
