# 一键喊话 · 技术方案调研

> 调研日期：2026-11-14　｜　对象：S10ykApp（106 应用板 + 103 业务板 + 手机浏览器）
> 状态：**待用户确认形态后进入设计/开发**

---

## 1. 需求可能的三种形态

「一键喊话」在巡逻机器人语境下有三种落地方式，技术难度差一个量级，需先确定：

| 形态 | 交互 | 本质 | 用户价值 |
|---|---|---|---|
| **A 实时对讲** | 按住按钮说话，机器狗喇叭**同时**放出来 | 手机麦克风 → 实时 PCM 流 → 103 声卡 | 现场喊话/疏导，最像"扩音器" |
| **B 录完即播** | 按住录音，**松手**后机器狗播放整段 | 手机录音 → 整段上传 → 播放 | 说错可重录，抗网络抖动 |
| **C 预置喊话** | 点固定语句按钮（"请注意避让"等）直接播 | 复用现有 `say_wav()` | 无需麦克风/HTTPS，最快落地 |

C 本质是现有「自定义语音」的快捷方式，**不新增技术风险**；真正的新能力是 A/B，二者都依赖手机麦克风。

## 2. 实测数据（本机 + 板上实测，2026-11-14 15:20）

| 验证项 | 方法 | 结果 |
|---|---|---|
| PCM 经 SSH 灌入 103 声卡 | 1s 正弦波 → `aplay -D plughw:0,0 -t raw -` | 总耗时 1711 ms（含建链 ~500ms + aplay 打开 ~200ms），**持续推流只付一次** |
| 100ms 分片持续推流 | 4s 音频按 3200B/100ms 喂入 | 总耗时 4732 ms、**rc=0、无断音** ✅ |
| 低延迟参数 | `--buffer-time=200000 --period-time=50000` | 4s/4628 ms、rc=0、稳定 ✅（比默认早 ~100ms 出声） |
| ALSA 默认缓冲 | `aplay -v` | buffer 8000 frames / period 2000 frames @16k = **500ms / 125ms**（后于 OPS-64 定为 `-B 250000 -F 50000` → 官方实测协商 4000/800 frames） |
| 声卡独占 | `plughw:0,0` 为独占设备 | 遗留的 `aplay -q -D plughw:0,0 -` 进程会**永久占用**（实测踩到 2 次，导致 "Device or resource busy"）→ 开流前必须清理 |
| PipeWire | `pactl list short sinks` | 默认 sink = `auto_null`（空设备），**不占真实声卡**，无冲突 |
| 板载 TTS | `which espeak piper` / 音色目录 | 仅 `espeak`（中文机械音，不可用）；`wav/lanxiaoyang/` 是**预录音频目录**，非 TTS 模型；板子无外网 → **文本转语音路线排除** |
| 带宽需求 | 16kHz × 16bit × 单声道 | 32 KB/s（256 kbps），Wi-Fi 无压力；8kHz 可降到 128 kbps |
| 机器人麦克风 | `arecord -l` | 103 有 6ch 麦克风阵列（`hw:1,0`，当前 `wakeup.enable=false`）→ 理论上可做双向对讲，但被 audio_node 占用风险高，暂不纳入 |

### 延迟预算（实时对讲 A）

```
手机采集 + 100ms 分片        ~100 ms
Wi-Fi/局域网上行             10~30 ms
106 后端转发                <5 ms
103 网络接收 + ALSA 缓冲     60~150 ms（200ms buffer / 50ms period）
--------------------------------------------
合计                        ≈ 200~300 ms（对讲级，人耳可接受）
```

### 关键发现（会改变方案的两条）

1. **声卡是独占资源**：现有 `say_wav()` 与喊话不能并行。喊话前必须 `say_stop()` + `pkill -f "aplay -q -D plughw"`，否则直接报 busy。
2. **麦克风需要安全上下文（HTTPS）**：`getUserMedia()` 仅在 HTTPS 或 localhost 下可用。当前页面 `http://10.21.33.106:8080` 在手机浏览器里**必然被拒绝**（微信内置浏览器同样拒绝）。这是 A/B 方案的**前置硬门槛**。

## 3. HTTPS 可行性

| 项 | 结论 |
|---|---|
| 106 是否具备 | `openssl 3.0.13` 可用，Python `ssl` 为标准库，`ThreadingHTTPServer` 可直接包一层 TLS ✅ |
| 证书 | 自签证书（CN=10.21.33.106），一次生成长期使用 |
| 端口 | 建议新增 **8443**（保留 8080 明文，便于调试与降级） |
| Android Chrome | 首次访问点「高级 → 继续前往」，之后麦克风可正常授权 ✅ |
| iOS Safari | 需下载并**手动信任**证书描述文件（步骤繁琐）；**微信内置浏览器不支持麦克风授权** ⚠️ |
| 局域网限制 | 无外网也可用（不依赖公网 CA） |

## 4. 方案对比

| 维度 | A 实时对讲 | B 录完即播 | C 预置喊话 |
|---|---|---|---|
| 延迟 | 200~300 ms | 松手后 0.5~1.5 s | <0.5 s |
| 需要麦克风 | ✅ 需要 HTTPS | ✅ 需要 HTTPS | ❌ 不需要 |
| 后端复杂度 | 高（流式接收 + 抗抖动缓冲 + 看门狗） | 低（一次 POST 整段） | 极低（复用现有接口） |
| 网络容忍 | 差（抖动会卡顿） | 好（失败可重试） | — |
| 说错可重录 | ❌ | ✅ | ✅ |
| 代码量估算 | 后端 ~180 行 + 前端 ~120 行 | 后端 ~70 行 + 前端 ~90 行 | 前端 ~30 行 |

## 5. 推荐路线

**第一步（MVP，半天）：方案 B —— 按住录音、松手即播**
- 链路最简单，先把「HTTPS + 麦克风授权 + 103 播放」这条主干打通；
- 松手到出声 ~1s，现场喊话完全够用；
- 录到的片段可顺手存成"喊话片段"，一键重播（等于 C 的升级版）。

**第二步（可选，1 天）：方案 A —— 实时对讲**
- 复用 B 的 HTTPS 与播放通道，前端改 `AudioWorklet` 边录边发（100ms/片）；
- 后端加流式接收（`Content-Length` 未知的 chunked body 顺序读）+ 200ms 缓冲 + 空闲看门狗。

先做 B 再做 A 的额外收益：B 的失败模式（证书没信任、麦克风被占用、声卡 busy）会被提前暴露，A 只是在其上做流式化。

## 6. 实施设计（按方案 B/A 共用骨架）

### 6.1 接口

```
POST /api/shout/clip      Content-Type: audio/wav      整段播放（B）
POST /api/shout/stream    Content-Type: audio/L16      流式播放（A，边收边写 aplay）
POST /api/shout/stop      停止喊话（同时清理 aplay 进程）
GET  /api/shout/state     返回 {active, seconds, bytes}
```

### 6.2 后端要点

```python
# 1) 开流前做互斥 + 清理僵尸进程（关键！）
audio_stop(0); say_stop()
_ssh103("pkill -9 -f 'aplay -q -D plughw' ; true")

# 2) 常驻推流进程（低延迟参数）
cmd = ["ssh", "-i", SSH_KEY, ..., SAY_HOST,
       "aplay -q -D plughw:0,0 --buffer-time=200000 --period-time=50000 "
       "-f S16_LE -r 16000 -c 1 -t raw -"]

# 3) 看门狗：3s 无新数据 or 客户端断开 → close stdin + kill
# 4) 与现有 /api/audio/{play,say} 双向互斥，状态进 /api/status
```

### 6.3 前端要点

- 「语音播报」卡下方新增 **🎤 一键喊话** 按钮：移动端**按住说话**、桌面端点击开始/结束；
- 采集：`getUserMedia({audio:{echoCancellation:true, noiseSuppression:true, channelCount:1}})` → `AudioWorklet` 降到 16kHz 单声道 PCM；
- 录制中显示**电平条 + 计时 + 停止键**，颜色沿用现有 `.eq` 动画风格；
- 播放中若用户切走页面 → 自动停止（避免占着声卡）；
- 失败提示要具体：「未授权麦克风」「需要 HTTPS」「设备忙，请重试」。

## 7. 风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| 回声啸叫（手机就在机器人旁边） | 刺耳 | 建议戴耳机；`echoCancellation=true`；增益默认 60%，可调 |
| 声卡被遗留 aplay 占用 | 喊话无声 | 开流前 `pkill`；失败自动重试 1 次并提示 |
| 厂商 audio_node 抢占声卡 | 偶发无声 | 检测 busy → 等待 300ms 重试；必要时先 `/api/audio/stop` |
| 网络抖动（A） | 卡顿/断续 | 100ms 分片 + 200ms 缓冲；连续 3 片丢失则重启流 |
| iOS 证书信任繁琐 | 无法用麦克风 | 方案 B 支持"先在电脑录好上传"的降级路径 |
| 长时间按住导致进程堆积 | 声卡卡死 | 看门狗：单次最长 60s，超时自动停 |

## 9. 双向对讲的硬件前提（2026-11-14 15:40 追加实测）

用户确定要**双向对讲**（MIC：手机→狗；SPK：狗→手机）后补测，结论不乐观：

| 方向 | 链路 | 状态 |
|---|---|---|
| MIC（手机→狗喇叭） | 手机麦克风 → HTTPS → 106 → ssh → 103 `aplay plughw:0,0` | ✅ **可行**（已实测 100ms 分片推流稳定） |
| SPK（狗麦克风→手机） | 103 `arecord` 或 `/AUDIO/RECORD_CMD` → 106 → 浏览器 | ❌ **当前不可行** |

SPK 方向的阻塞点（详见《实现方式审计_话题与硬件.md》）：

1. `/AUDIO/RECORD_CMD` 话题**有接口未实现**：`audio_ctl record start 2` 直接 `Aborted (core dumped)`，`/AUDIO/RECORD_STATUS` 无发布者；
2. 硬件直取 `arecord -D plughw:1,0` 报 **Device or resource busy**；停掉 PipeWire 后仍 busy（`PREPARED / owner_pid=0`，疑为崩溃残留句柄）；
3. `arecord -D default` 走 PulseAudio 插件，录到的是**纯静音**（RMS=0）。

**建议**：先按单向（手机→狗）实现喊话；SPK 方向待定位麦克风占用者（需 103 root 或重新插拔 USB 音频模块）后再评估。

## 10. 结论

- 技术主干**已实测可行**：PCM 经 SSH 实时灌入 103 声卡，100ms 分片稳定无断音，延迟预算 200~300ms。
- 唯一硬门槛是**手机麦克风需要 HTTPS**，106 具备自签能力，安卓侧代价很小。
- 推荐 **B 先行、A 进阶**，C 可随时作为兜底（零风险）。

### 11.2 官方"一键喊话"是怎么做的（关键发现）

官方喊话**不是机器狗本体能力，而是 M20 警用的外挂"二代多合一/四合一"载荷**，与 S10 本体的实现路径完全不同：

| 维度 | 官方 M20 警用方案（在线 259676030 / 259676029） | 本项目 S10 Pro 现状 |
|---|---|---|
| 喊话硬件 | 外挂**二代多合一**，15 W 喇叭、**110 dBA@1 m**；另有 8 咪头收音（建议 5 m） | 本体自带扬声器（无功率/声压参数）+ 多阵列麦克风 |
| 喊话输入 | **G20 手柄麦克风**：点"开始喊话"→说话→再点"停止"（即 Press-to-talk 两次点击，非按住） | 无手柄集成；网页控制台为主 |
| 收音 | 设备端 8 咪头采集→G20 播放；**喊话/收音切换注意啸叫** | `arecord` 硬件被占、`/AUDIO/RECORD_CMD` 有接口未实现（见 §9） |
| 附加能力 | 警报、文字转语音（男/女声+循环）、音频文件（mp3/wav/flac/aac） | 系统音 9 条（DDS）+ 自定义 wav（sayd）；**无 TTS** |
| 控制接口 | 私有协议文档 `_38_喊话协议_20260330.doc`、`_38_狗版小四合一协议_20260330.xls`（需售后提供） | 公开接口只有 `/AUDIO/COMMAND`（预设 id）、sayd（PCM 推流） |
| 供电/连接 | 本体 4 号复合口 24 V/3 A + 网口 → 二代多合一 | 无此外挂载荷 |

**官方接口边界（原文）**：二代多合一可实现"喊话、收音、文字转语音、音频、照明和红蓝警示控制"，配套私有协议文档需联系售后获取——即官方把喊话当成**付费外挂载荷 + 私有协议**，不是本体开放 API。

### 11.3 对 S10 本体的可行性判定

1. **S10 本体走官方喊话路径 = 不可行**：S10 软件开发指南全文 42843 字符，`audio`/`AUDIO`/`麦克`/`扬声`/`喊话`/`TTS` **0 命中**；硬件手册无音频接口定义；本体无二代多合一口径说明。官方喊话方案（载荷+协议）不适用于 S10 本体。
2. **本体仅有的音频能力**（来自本地实测审计《实现方式审计_话题与硬件.md》）：
   - 系统音 9 条：`/AUDIO/COMMAND` → 厂商 audio_node（DDS，预设 id，无法播任意内容）；
   - 自定义 wav：TCP → 103 常驻 `sayd`（:18081，帧 START/PCM/STOP）→ `aplay -D plughw:0,0`，**任意 PCM 都能播**；
   - 音量：`amixer`（无占用）；
   - 收音：`/AUDIO/RECORD_CMD` core dumped、`arecord` 硬件 busy——**SPK 方向（狗→手机）仍不可行**（同 §9）。
3. **因此 S10 上"一键喊话"唯一现实路线 = 复用现有 sayd 通路做"手机→本体扬声器"单向喊话**（即第 2 节的方案 A/B），官方外挂方案只能作为需求对标与"高声压/双向对讲需另配硬件"的依据。

### 11.4 推荐落地方案（结合现有语音播报，改动最小）

基于"sayd 已能推任意 PCM"这一现成能力，**不新增硬件、不动厂商 audio_node**，分两级：

**一级（推荐先做，对应原方案 B「录完即播」）——复用 say_wav 骨架：**
- 前端按住录音（`getUserMedia` + `AudioWorklet` 降 16 kHz 单声道），松手得到整段 PCM/WAV；
- 新增 `POST /api/shout/clip`：后端把收到的 WAV 存临时文件 → 直接调现有 `say_wav()` 播放；
- 复用现有互斥：`say_stop()` + `audio_stop(0)` 保证与系统音/自定义播报不叠音；
- 麦克风授权硬门槛不变（需 HTTPS 自签，见 §3）；安卓可行、iOS/微信内置浏览器受限。

**二级（进阶，对应原方案 A「实时对讲」）——sayd 天然适配流式：**
- sayd 协议本就是 `START → 多片 PCM → STOP` 的流式模型（当前 say_wav 按 3200 B/100 ms 推片），与实时喊话几乎同构；
- 新增 `POST /api/shout/stream`（chunked 边收边推 sayd）+ 200 ms 抗抖缓冲 + 3 s 看门狗；
- 延迟预算 200~300 ms（同 §2），人耳可接受；
- 风险：声卡独占（开流前 `say_stop()` + `pkill` 僵尸 aplay）、回声啸叫（建议耳机 + `echoCancellation`）、切页面自动停止。

**C 预置喊话（零风险兜底）**：现有语音面板里"保持 3m 距离"等 wav 已是现成一键播，可作为喊话需求的最小可用版本先行交付。

### 11.5 结论（更新）

- **官方**：喊话是 M20 警用外挂载荷（二代多合一 + 私有协议 + G20 手柄麦克风）的能力，S10 本体无官方喊话接口；你给的在线链接是硬件手册，本身不含喊话内容。
- **本体**：S10 有扬声器 + 多阵列麦克风，但收音链路当前不可用（`RECORD_CMD` 崩溃、硬件 busy）；喊话只能做**单向（手机→狗）**。
- **落地**：最佳路径是**复用 speak 通路（sayd）**——先做"录完即播"（改动最小、抗抖），进阶做实时对讲（sayd 流模型天然适配）；高声压（官方 110 dBA 级）与双向对讲属外挂硬件范畴，如项目需要须另配二代多合一声光载荷并索取私有协议。
- **前置门槛不变**：手机麦克风需 HTTPS（§3）；这是 A/B 方案能否落地的唯一硬条件。
