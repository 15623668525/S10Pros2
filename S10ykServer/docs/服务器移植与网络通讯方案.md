# 服务器移植与网络通讯方案（2026-11-15 凌晨实测）

> 需求：调研将控制台应用移植到服务器 **<SERVER_IP>**（SSH 端口 625，root），输出**实际的网络通讯方案**。
> 前提：`<ROBOT_IP>` 与服务器"直通"——**实测该 IP 配在 103 的 wlan0 上**（DHCP 自网关 <SITE_GW>），并非 106 的板载网口。

## 一、结论先行

| 问题 | 答案 |
|---|---|
| 链路是否打通？ | **全部打通（端到端实测通过）**：用户浏览器→公网入口→服务器→机器人，四段全部验证 |
| 机器人怎么接服务器？ | 103 wlan0 = `<ROBOT_IP>/16`，与服务器 `ens16f0(<SERVER_IP>/16)` **同网段二层直通**，RTT **2.4–12ms**，质量极好 |
| 106 能否直接上服务器？ | 不能。106 无公网 IP、无默认路由（隔离内网 10.21.33.0/24）；必须**经 103 中转**（103 eth0=10.21.33.103 与 106 同网段，天然是路由桥） |
| 应用怎么移植？ | **s10yk 后端必须留在 106**（rclpy/DDS 与厂商节点同网段，无法跨网段组播）；服务器上部署「前端托管 + API 反向代理 + 视频转码」，经 103 反向 SSH 隧道访问 106 后端 |
| 服务器能不能拉机器人视频？ | **能**。服务器 `ffprobe rtsp://<ROBOT_IP>:8554/video0` 实测成功：h264 / 1024×576 / 30fps |
| 用户从哪里访问？ | 公网入口 `<FRP_IP>`（服务器 frpc 已在用），本机实测 20022/20024/80 端口全通 |

## 四、实际网络通讯方案（推荐架构）

### 4.1 架构图

```
[控制台浏览器]
     │ ① HTTPS/WS（公网）
     ▼
<FRP_IP>:20081 ──frp──> <SERVER_IP>:8081 (nginx)
                                 │            │
                     ② /api/* 反向代理     ③ /cam/* 视频
                                 │            │
                                 │      ffmpeg（NVENC）
                                 │            │ rtsp://<ROBOT_IP>:8554/videoN
                     ④ SSH 反向隧道 127.0.0.1:19080
                                 │            │
                                 ▼            │
                    103 (<ROBOT_IP>) ─────┘
                                 │ 103 内部路由
                                 ▼
                     106:8080 s10yk 后端（rclpy/DDS，原地不动）
```

### 4.2 四条通路逐条说明

**① 用户 → 服务器（公网入口）**
复用服务器现有 frpc：`frpc.toml` 追加一段
```toml
[[proxies]]
name = "s10yk-console"
type = "tcp"
localIP = "127.0.0.1"
localPort = 8081
remotePort = 20081
```
`frpc reload -c /etc/frp/frpc.toml` 热生效。用户浏览器访问 `http://<FRP_IP>:20081`。
（若后续申请到服务器公网安全组放行，可直连 <SERVER_IP>:8081，frp 仅作备份。）

**② 控制 API（浏览器 → 106 后端）**
机器人主动向服务器**反向 SSH 隧道**（已实测 T6 成功）：
```bash
# 103 上以 systemd 常驻（autossh 保活）：
autossh -M 0 -fN -o ServerAliveInterval=15 -o ServerAliveCountMax=3 \
  -R 19080:10.21.33.106:8080 -p 625 root@<SERVER_IP>
```
服务器 nginx 反代 `/api/` → `http://127.0.0.1:19080/api/`。
- 机器人侧主动外连，服务器无需路由到 10.21.33.0/24（T4 已证不可路由）；
- 隧道断线 autossh 自动重连；DDS 无法跨网段组播，**所有控制必须收敛在 106 后端的 HTTP API**——现有架构本来就是这样，前端零改造。
- 时延预算：浏览器→frp 公网（视线路）+ 服务器↔机器人 RTT ≈5ms + HTTP 往返 ≈ **<80ms**，遥控体感无差异。

**③ 视频（103 RTSP → 服务器转码 → 浏览器）**
服务器直接拉 `rtsp://<ROBOT_IP>:8554/video0`（T5 已证），在服务器上转码：
```bash
ffmpeg -rtsp_transport tcp -i rtsp://<ROBOT_IP>:8554/video0 \
  -vf scale=960:-2 -r 15 -c:v h264_nvenc -preset p1 -tune ull -g 30 \
  -f flv rtmp://127.0.0.1/live/front   # 或 mse/websocket 方案
```
- 106 上跑 ffmpeg 转码（v2.6 已实现 MJPEG 方案）改为**服务器跑**：106 8 核省下 54% 单核开销，且 4090 NVENC 时延更低；
- 前端仍走 `/cam/*` 接口，来源从"106 本机 ffmpeg"换成"服务器 ffmpeg"，协议不变或升级为 WS-MSE/WebRTC（低时延 200–500ms）；
- 4 路机位 `video0/2/4/6` 同理，按需拉流，不看不停。

**④ 语音/文件维护通路**
- 语音播报链路（`/api/audio/*` → 106 → 103 sayd）全部收敛在 106 后端内部，走 ② 即可，不需要新通路；
- 服务器部署/升级代码：服务器 → 103 (<ROBOT_IP>:22) → 106，SSH 跳板两跳；或经公网 20023 直达 103。

### 4.3 安全要点（上线前必做）

1. frp 已带 token，但**公网入口是明文 HTTP**：控制台无鉴权（遗留 D-003），上公网前必须加一层（nginx basic auth / token / VPN）——**否则任何人都能急停/喊话/遥控机器人**；
2. 建议给 20081 前面加 nginx TLS（自签证书或域名+Let's Encrypt）；
3. 103/106 的 SSH 密码认证建议改密钥，避免 fail2ban 误封与弱口令风险；
4. 服务器上 frpc 配置含 token，改动用 `frpc reload` 热加载，勿重启 frpc 影响他人代理（20022/20023/20024 是别人的在用通道）。

## 七、后端整体上服务器？DDS 跨网段专项实测（2026-11-15 07:00 补充）

> 问题：控制指令必须经 106 后端转 DDS（DDS 组播不跨网段），那能不能把后端整体搬到 <SERVER_IP>？备选路径：103 DNAT / 103+106 起 WS 转发 / 其他。

### 7.1 为什么 DNAT 和"组播路由"都是死路（实测）

| 实验 | 结果 | 结论 |
|---|---|---|
| 服务器监听 DDS 组播 239.255.0.1 | 15s 只收到**自己发的**组播，零个机器人发现包（106 侧同时确认组播正以 ~44ms 间隔在跑） | **二层组播不跨 AP**——机器人 DDS 发现包根本出不了 10.21.33.0/24 |
| FastDDS 配置（`/opt/robot/fastdds.xml`） | SHM+UDP 双传输，发现走 239.255.0.1 组播，TTL=1 | DNAT 只能改单播；组播 TTL=1 路由转发即丢，**DNAT 无法承载 DDS 发现** |
| drdds 包形态 | **纯 Python**（`/opt/ros/jazzy/.../site-packages/drdds`，无 aarch64 编译产物，import 验证通过） | 如需在 x86 服务器直接参与 DDS 域，消息包可直接拷贝 |

### 7.2 可行解：zenoh-bridge-dds 应用层桥接（已端到端实测打通）

```bash
# 下载（服务器 github 直连可用）
#   x86_64: zenoh-bridge-dds 1.5.0 → /opt/zenoh/  （服务器）
#   aarch64: 同版本 → 103:/tmp/zenoh-bridge-dds   （chmod +x）
# 服务器端（先放行防火墙，只对机器人网段开）：
ufw allow from <SITE_NET>/24 to any port 7447 proto tcp    # 否则 zenoh 永远连不上
/opt/zenoh/zenoh-bridge-dds --listen tcp/0.0.0.0:7447
# 103 端（连服务器）：
/tmp/zenoh-bridge-dds -e tcp/<SERVER_IP>:7447
```

**实测结果**：

| 项目 | 结果 |
|---|---|
| 话题发现 | 103 bridge 一启动即发现机器人全部 DDS 话题（MOTION_INFO/GAIT/BATTERY_DATA/导航/重定位服务等），双向路由自动建立 |
| 数据下行（机器人→服务器） | 服务器直订 `rt/MOTION_INFO`：**20.0 条/s** 稳定收到（与 106 本机一致，52B CDR） |
| 数据上行（服务器→机器人） | 服务器发 `rt/ZPING`(StdMsgInt32) → 106 回声节点收到并回 `/ZPONG` → 服务器收到。**上行链路证实** |
| **全链路往返时延** | 服务器↔106 完整 DDS 往返（含两次 DDS 桥接+无线段）：**min 4.6 / p50 6.2 / avg 8.6 / p95 23.5 / max 29.2 ms**（30 样本） |
| 服务器侧订阅方式 | `mode=peer` + `connect: tcp/127.0.0.1:7447`（默认组播侦察在同机 bridge 上不可靠，必须显式连） |

### 7.3 由此产生的两种后端架构

| | 方案甲（现方案）：后端留 106 | 方案乙：后端整体上服务器 |
|---|---|---|
| 原理 | 服务器 nginx → 103 反向隧道 → 106:8080 | app.py 跑在服务器（装 ROS2 jazzy + 拷 drdds），其 DDS 端点与服务器 bridge 在服务器局域网互通，经 zenoh 隧道触达机器人 |
| 后端改动 | **零** | 小（环境迁移 + MOTION_INFO 20Hz 走桥接，实测带宽可忽略） |
| 额外组件 | autossh 隧道 | 2× zenoh-bridge-dds（systemd 常驻） |
| 时延 | 控制 ~5–30ms（反向隧道 ssh 转发） | 控制 ~5–30ms（实测 RTT） |
| 断链行为 | 隧道断→公网不可控，内网直连不受影响 | zenoh 自动重连；机器人本体不受影响 |
| 风险 | 103 无线断→公网全断（有 eth1 有线备选） | 服务器 bridge 是单点；服务器 reboot 需自愈 |
| 适用 | 快速上线（当前推荐） | 后续把 AI/导航算力放上服务器时的自然演进 |

> 结论：**后端可以上服务器，方案乙已被证实可行**（关键障碍组播不跨网段 → 用 zenoh-bridge-dds 应用层桥接绕开）。两种方案的桥接基础设施完全相同，可以先甲后乙平滑演进。

### 7.4 正式部署（systemd 常驻，2026-11-15 08:30 验收通过）

**服务器 <SERVER_IP>**（`/etc/systemd/system/zenoh-bridge-dds.service`）：

```ini
[Service]
Environment=CYCLONEDDS_URI=file:///opt/zenoh-dds/cyclonedds.xml
Environment=RUST_LOG=info
ExecStart=/opt/zenoh-dds/srv/zenoh-bridge-dds -l tcp/0.0.0.0:7447
Restart=always
RestartSec=5
```

配套 `/opt/zenoh-dds/cyclonedds.xml`：显式声明 `lo + ens16f0 + ens16f1` 三块网卡参与组播发现（**多网卡服务器必须配**，否则 bridge 的 DDS 参与者绑定错网卡，与本地 rclpy/drdds 进程互相"失明"——这是本次最大的坑，症状是 zenoh 层数据正常、DDS 层双向全断）。

**103 端**（`/etc/systemd/system/zenoh-bridge-dds.service`，root 运行）：

```bash
ExecStart=/opt/zenoh/zenoh-bridge-dds -c /opt/zenoh/bridge-103.json5 -e tcp/<SERVER_IP>:7447
```

`bridge-103.json5`：`timestamping.enabled=false` + 关闭组播侦察（原因见 7.5）。

### 7.5 排障实录与运维红线（2026-11-15 上午，3 个关键坑）

**坑 1：多网卡服务器上 bridge 的 DDS 参与者绑定错网卡。**
症状：zenoh 层一切正常（zenoh-py 订 `rt/MOTION_INFO` 有 20Hz 数据），但服务器本机 rclpy/drdds 订阅 DDS 话题永远 0 条，bridge 日志一条 Route 都不打。定位：zenoh-py 与 rclpy 分层对照 + admin space（`@/**`）确认 bridge 本地参与者无 writer。修复：CYCLONEDDS_URI 显式指定全部业务网卡。**分层验证法（zenoh 层订阅 + DDS 层订阅分开测）是排障关键。**

**坑 2（2026-11-16 已根治，原结论有误）：103 业务板系统时钟比真实 UTC 快 ~48→52 秒。**

真因不是"厂商跨板对时锁死"，而是 Ubuntu 的 `chronyd-starter.sh` 把厂商加固过的系统**误判为容器**，自动给 chronyd 加了 `-x`（禁用控钟）：日志 `Warning: Running in a container ... Adding -x as fallback`。所以尽管 chronyd 早已配置 `server <SERVER_IP> iburst prefer` 且 `Reach 377`，`System time` 始终是 `51.94s fast`——它知道偏了多少，但不许改。

修复（一行）：`/etc/default/chrony` 的 `SYNC_IN_CONTAINER="no"` → `"yes"`，重启 chrony，立即 step -51.9 s。验证：三机 `date` 差 <0.5 s、106→103 SNTP 1 ms、服务器 zenoh `exceeding delta` ERROR 归零。另外厂商 MCU 对时方向是**板→MCU**（步进后 dmesg `send time_diff: -51934ms`），所以板卡时间准了，MCU 也跟着准。

> 已作废的旧红线：~~不要试图校准 103/106 的系统时钟、不要在 106 上叠加 NTP 服务~~。现行规则：时钟只由 103 的 chronyd（对 204）与 106 的厂商 PTP 负责，**不要再手工 `date -s`，也不要装第二套 NTP 客户端**。
> 运维红线：**不要试图校准 103/106 的系统时钟**（厂商机制会拉回），不要在 106 上叠加 NTP 服务；时钟一致性由"103 端 bridge 关时间戳"保证。

**坑 3：zenoh-bridge-dds 版本与本地订阅方式。**
服务器 v1.10.2、103 v1.5.0，跨版本桥接实测兼容。但服务器本机 zenoh 客户端必须显式 `connect tcp/127.0.0.1:7447`（组播侦察不可靠）；服务器 ros2 CLI 未装，验证用 rclpy + `/opt/s10yk/install/setup.bash`（注意工作空间在 `/opt/s10yk` 下，不是 `ros2_ws` 子目录）。

## 八、方案乙组件详解（每个组件是什么、为什么需要、怎么配）

### 8.1 总览：数据是怎么从浏览器走到电机和喇叭的

```
浏览器
  │  HTTP(控制/状态) + MJPEG(视频)
  ▼
frpc(服务器) ──公网隧道──► frps(<FRP_IP>)   ← 服务器不对公网开放，frp 是唯一入口
  ▼
nginx :8081        ← 前端静态文件 + /api 反代到本机后端
  ▼
app.py :18080      ← 【已搬到服务器】解析 REST，经 rclpy 读写 DDS
  ▼
rclpy → FastDDS    ← 服务器本机的 DDS 参与者（与 106 上跑时完全同构）
  ▼
zenoh-bridge-dds(服务器) ←桥①→ zenoh 隧道(TCP 7447) ←桥②→ zenoh-bridge-dds(103)
  ▼
机器人内网 DDS 域(10.21.33.0/24 组播) → 厂商运动控制/音频节点
（旁路：语音文件 → sayd(103:18081)；视频 ← RTSP(103:8554) ← ffmpeg(服务器)转码）
```

### 8.2 DDS（Data Distribution Service）—— 机器人内部的"神经系统"

- **是什么**：对象管理组织(OMG)标准的发布/订阅中间件。跟 MQTT/Kafka 不同，它**用 UDP 组播做自动发现**：新节点上线后向 239.255.0.1 发 discovery 包，域内所有节点自动认识它，无需任何 broker 和配置。
- **在本机的作用**：厂商运动控制、音频、导航节点全部通过 DDS 通信，话题如 `/MOTION_STATE`（下发状态）、`/MOTION_INFO`（20Hz 回报高度/姿态）。**DDS 组播 TTL=1 且不能跨网段**，这就是机器人内网和外网必须"桥"的根本原因。
- **FastDDS**：厂商选的 DDS 具体实现（eProsima），配置在 `/opt/robot/fastdds.xml`：SHM+UDP 双传输。改这份配置=动厂商域，**我们不动它**。

### 8.3 drdds —— 厂商的私有消息定义包

- **是什么**：厂商自定义的 ROS2 消息类型集（`MotionInfo`、`Gait`、`BatteryData`…），本质是一个**纯 Python** 的 site-packages 目录（无 aarch64 编译产物），安装于 106 的 `/opt/ros/jazzy/lib/python3.12/site-packages/drdds`。
- **为什么重要**：DDS 传输的是二进制 CDR 序列化数据，**订阅方必须有同一套消息定义才能解包**。它是纯 Python 意味着整个目录 `cp` 到 x86 服务器即可用（已验证 import 通过），跨架构零成本。
- **注意**：`app.py` 还用了 `std_msgs.Float64MultiArray`（发 /AUDIO/COMMAND），所以 std_msgs 也要在服务器就位（apt 装 `ros-jazzy-std-msgs`）。

### 8.4 rclpy / ROS2 jazzy —— 后端与 DDS 之间的"驾驶舱"

- **是什么**：ROS2 的 Python 客户端库。app.py 用它 `create_publisher` / `create_subscription` 操作 DDS 话题。
- **关键点**：rclpy 的核心是 **C 扩展**（`_rclpy_pybind11...so`），**不可跨架构拷贝**——所以服务器必须 apt 安装 `ros-jazzy-rclpy + ros-jazzy-rmw-fastrtps-cpp`（RMW 是 rclpy 到 FastDDS 的绑定层，两端 RMW 实现不同也能互通，因为 DDS wire format 是标准）。
- **在 106 上**：源 ROS 环境 `source /opt/ros/jazzy/setup.bash`；在服务器上同理（systemd 单元里 ExecStart 前置 source）。

### 8.5 zenoh —— 桥接用的"轻量级云原生总线"

- **是什么**：Eclipse 基金会的 pub/sub/query 协议栈（Rust 实现）。和 DDS 的区别：**发现不靠组播靠显式连接**（`tcp/ip:port`），天然适合跨网段/跨广域；开销极小（RTT 实测受限于物理网络而非协议）。
- **在本方案的角色**：103 与服务器之间那条"穿透网段"的隧道就是 zenoh 会话。不选 MQTT 是因为 zenoh-bridge-dds 官方现成、自动做 DDS 话题映射，零开发。
- **安全**：当前靠 ufw 把 7447 限制在 <SITE_NET>/24（只有 103 能连）。正式版建议再加 zenoh token 鉴权（`--cfg` 里配 auth）。

### 8.6 zenoh-bridge-dds —— 本方案的"主角"，两侧各一个

- **是什么**：一个单二进制（Rust，~20MB）的**协议网关**。它同时是两个世界的公民：
  - 在 DDS 世界里，它是一个**普通 DDS 参与者**（跟厂商节点一样发组播发现、收发 CDR 数据）；
  - 在 zenoh 世界里，它是一个**普通 zenoh 节点**（跟对端 bridge 建一条 TCP 长连接）。
- **工作原理（自动路由）**：
  1. 103 端 bridge 加入机器人 DDS 域 → 发现"有个发布者正在发 `/MOTION_INFO`"；
  2. 自动创建路由：DDS `/MOTION_INFO` ↔ zenoh `rt/MOTION_INFO`（加 `rt/` 前缀避免和 zenoh 自身命名冲突），类型信息（`drdds::msg::dds_.MotionInfo`）随路由记录；
  3. 服务器端 bridge 收到 zenoh 声明 → 在服务器局域网**重建一个等价的 DDS 发布者**；
  4. 服务器上的 app.py 看到的就像机器人本机在发一样。反向（MOTION_STATE 下行）同理。
  - 路由是**双向、按需、自动**的：任何一侧出现新话题/新订阅者，桥自动建路由，无需配置话题清单。
- **实测表现**：发现全部厂商话题；MOTION_INFO 20Hz 无丢帧；全链路 RTT 中位 6.2ms。
- **坑（已记入 OPS）**：①服务器 ufw 默认 DROP，7447 不放行则 zenoh 永远握手失败；②zenoh 连接失败时 bridge **不会无限重试**，防火墙放行后要重启 103 端；③同一台机器只能跑一个实例（多实例会互相抢路由）。

### 8.7 sayd —— 自研的"音频播放代理"（保持在 103）

- **是什么**：我们写的常驻小服务（103:18081，TCP 协议）。后端把 16k/mono/16bit PCM 流推给它，它负责按需打开 103 声卡、播完即释放。
- **为什么留在 103**：声卡物理上在 103（ES8323），且厂商音频节点也在 103 本地——播放这件事必须贴着硬件做。
- **方案乙的适配**：app.py 搬到服务器后，`SAYD_HOST=<ROBOT_IP>`（103 的直通网 IP）即可，协议不变。音量调节/进程守护用 SSH key（服务器新配一把钥匙装进 103 的 authorized_keys）。

### 8.8 RTSP + ffmpeg —— 视频通路

- **RTSP 源**：厂商相机节点在 103:8554 输出 4 路 H.264（1024×576@30）。服务器现在**直连** `rtsp://<ROBOT_IP>:8554/videoN`（已 ffprobe 验证）。
- **ffmpeg**：把 H.264 转成浏览器能直接看的 MJPEG（低时延参数）。原来跑在 106（占单核 54%），方案乙里**转码挪到服务器**——106 的 8 核 ARM 省下来，服务器 48 核随便用（以后还可切 NVENC 硬件转码）。app.py 的 `RTSP_BASE` 环境变量已支持此切换。

### 8.9 nginx —— 原计划的"前端托管 + 反代"，实测后**不采用**

- **原设想**：①把 `frontend/index.html` 作为静态站点；②把 `/api/*` 反代到 app.py；③预留 TLS/Basic Auth 位置。
- **实测否决原因**：
  1. **后端本来就同源托管前端**——app.py 的 `do_GET` 里 `path in ("/", "/index.html")` 直接吐 index.html（21906B→25048B），前端全部用相对路径调 API，没有跨域问题，"静态/动态分离"这套前提不存在；
  2. **8081 已被 NVR web 占用**（`/data/nvr/web/app.py`，pid 308848，返回重定向页），nginx 用 8081 会直接撞端口；
  3. **服务器没装 nginx**（`which nginx` → 空），为一个不需要的层额外装包、写配置、加故障点；
  4. **并发没问题**——app.py 用的是 `ThreadingHTTPServer`，MJPEG 长连接不会阻塞 `/api`。
- **什么时候再上 nginx**：只需要一个理由——**HTTPS**（访问口令已由 app 层 v2.7 用 `S10YK_TOKEN` 解决，不必再靠 Basic Auth）。届时端口用 **8082**（避开 NVR 的 8081），配置要点：证书 + `proxy_buffering off` + `proxy_read_timeout 3600s`（MJPEG 长连接必须关缓冲，否则画面会攒几秒才出一帧）。

### 8.10 frp（frpc/frps）—— 公网入口（20081 段已停用）

- **现状**：服务器上 frpc 常驻（`/opt/frp/frpc -c /etc/frp/frpc.toml`，systemd `frpc`），frps 位于 <FRP_IP>:7000。原有代理：20022（本机 ssh 625）、20023（机器人 205:22）、20024（机器人 205:8554 RTSP）。服务器 204 本体不对公网开放（全端口实测超时），frp 是唯一公网入口。
- **已追加**（2026-11-15）：`s10-console-18090`，`localIP=127.0.0.1 localPort=18090 → remotePort=20081`；用 `frpc reload -c /etc/frp/frpc.toml` **热加载**（webServer 7400 已启用），三条既有代理无中断。
- **已停用（2026-11-15 10:08，取消公网访问）**：`s10-console-18090` 段在 `/etc/frp/frpc.toml` 中整体注释掉（行首 `#`），`/opt/frp/frpc reload` 热加载，日志确认 `proxy removed: [s10-console-18090]`；实测外部直连 20081 = **连接被拒（curl exit 7）**，20022/20023/20024 **无中断**。恢复：去掉该段行首 `#` → `frpc reload`。
- **当前访问入口**：仅 `http://<SERVER_IP>:18090`（机器人内网，实测 17ms）。
- **备份**：改动前 `cp -a /etc/frp/frpc.toml /etc/frp/frpc.toml.bak-<时间戳>`。
- **带宽实测**：公网 MJPEG 约 **1.7 Mbps / 4.6 fps**（局域网 3.9 Mbps / 10.6 fps），frps 侧带宽是瓶颈——公网看视频能看但偏低，高质量遥控建议走内网入口。

### 8.11 systemd —— 进程自愈

- 每个常驻组件一个单元：`zenoh-bridge-dds.service`（服务器+103）、`s10yk-backend.service`（服务器）、`s10yk-say.service`（103，已有）。统一 `Restart=always` + `After=network-online.target`。
- 服务器断电/重启后：bridge 自愈 → zenoh 重连 → app.py 的 DDS 自动重新发现，无需人工干预。
