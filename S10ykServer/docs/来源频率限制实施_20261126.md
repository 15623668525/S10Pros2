# 来源频率限制实施（v3.5.10）

- 日期：2026-11-26
- 目标：给公网直连的后端加一层**最简单的按来源 IP 频率限制**，挡住扫描器/爆破工具的高频请求（v3.5.9 修复 TLS accept 阻塞后遗留的最后一个可选项）。

## 一、前提核实：限流按什么键？

部署 204 后查证（ss / ufw / frpc.toml）：

- frpc 中 18090 的公网映射（7305）**2026-11-15 已停用**，frps 已换 <FRP_IP>；
- 实际公网通路 = ufw 规则 11/16 直接放行 `18090 / 18443 → Anywhere`，即**公网直连 204 本机**；
- 结论：后端 `self.client_address[0]` 就是真实公网来源 IP，按 IP 限流**有效**，无需 frp proxy-protocol。

## 二、实现（纯标准库，~50 行）

`backend/app.py` 新增：

- `RL_WINDOW_S=2`、`RL_MAX=120`（环境变量 `S10YK_RL_WINDOW` / `S10YK_RL_MAX` 可调）
- `rate_limit(ip)`：每 IP 一个 `deque` 时间戳的滑动窗口；窗口内 ≥120 即返回 False
- `_is_private_ip()`：`10.x / 127.x / 192.168.x / 172.16-31.x / ::1 / ::ffff:映射` 豁免
- 防膨胀：追踪 IP 数上限 1024，满了淘汰最久不活跃项
- 挂载点：`do_GET` / `do_POST` 最顶部（POST 在读 body **之前**，超限来源不浪费 8MB 上传 IO）
- 超限响应：`429 {"error":"rate limited"}` + `Connection: close` + `close_connection=True`
  （POST 未读 body 时连接流已失步，keep-alive 复用会解析出垃圾请求，必须断连）

## 三、阈值依据（不误伤正常使用）

前端峰值请求率实测/推算：

| 来源 | 频率 |
|---|---|
| /api/nav 摇杆保活 | 10/s |
| /api/status 轮询 | 2/s |
| 对讲上行 /api/shout/pcm | ~10/s |
| 对讲下行 /api/talk/pcm | ~5/s |
| 人员页轮询 | 1/s |

峰值 ≈ 27 请求/s = 54 个/2s 窗口，限 120 余量 >2 倍；公网扫描器数百 req/s 被立刻挡住。

## 四、验证（公网真实链路）

1. 单元自测：窗口打满恰好 120 放行、私网 5000 次全放行、IPv6 映射/172 段边界正确、多 IP 隔离 ✅
2. 公网实测（本机 → `https://...:18443/`，220 并发）：
   - **结果：120 个 200 + 100 个 429，精确命中阈值，1.4s 内完成**
   - 服务端日志：`RATE LIMIT GET / from <本机公网IP>` ✅
3. 风暴后服务健康：`systemctl is-active` = active，127.0.0.1 `/api/auth` 200（私网豁免路径正常），人员检测播报业务无中断 ✅
4. 部署 MD5：`b8cc86d93242daf4288a18eb14836d87`（备份 `app.py.bak.ratelimit_20261126`）

## 五、遗留与建议

- **鉴权 OFF**：unit 文件未设 `S10YK_TOKEN`，启动日志 `auth: OFF`——公网开放端口 + 无令牌 = 任何人可控制狗。建议尽快在 unit 文件补 `Environment=S10YK_TOKEN=...` 并 `daemon-reload`（前端已有登录页，影响面小）。
- 回滚：`cp app.py.bak.ratelimit_20261126 app.py && systemctl kill -s SIGKILL s10yk-backend && systemctl start s10yk-backend`。
